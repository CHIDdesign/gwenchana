# 테스트 시스템 구축용 샘플 4개

작성일: 2026-11-12. 기준: [기대 동작 명세](../../docs/qa/EXPECTED_BEHAVIOR.md)의 v0.2 정책을 이어받은 v0.3, `QA-PROPOSAL-01`.

**이 폴더를 동료에게 전달하면 된다.** 네 개의 JUnit 4 테스트에 입력·순서·검증문을 작성했다. 동료의 작업은 테스트 본문을 새로 설계하는 것이 아니라, `QaAdapters`의 연결 함수와 시간·저장·네트워크 제어를 구현해 **실제 앱 코드**에 붙이는 것이다.

현재는 제품 연결 전이다. 샘플은 기존 Gradle 테스트에 등록하지 않았고, 등록 후 어댑터 없이 실행하면 `BLOCKED_ADAPTER`로 실패한다. `@Ignore`로 숨기거나 가짜 구현을 붙여 앱 테스트가 통과했다고 보고하지 않는다. 앱 기능 구현과 테스트 시스템 구축은 별도 작업이다.

## 파일과 읽는 순서

1. 이 README: 네 시나리오와 구현 범위.
2. [QaSampleTest.kt](QaSampleTest.kt): 정확히 4개의 `@Test`. 순서와 합격 판정.
3. [QaFixtures.kt](QaFixtures.kt): 고정 입력. 계정·사고 시각·임시/완성본·센서 벡터.
4. [QaAdapters.kt](QaAdapters.kt): 앱 연결 인터페이스와 관찰값. `Harness`는 시험 대상과 외부 입력을 연결하는 장치라는 뜻이다.

| 케이스 | 주요 영역 | 명세 연결 | 현재 상태 | 시스템에 필요한 기능 |
|---|---|---|---|---|
| TC-01 | 센서 보정·임계값 | SAMPLE-01, DET-01 | 기존 계산 경로에 연결 필요 | 원시 Float 입력, 콜백 관찰, 초기 상태 격리 |
| TC-02 | 완성본 전달 확인 | SAMPLE-02, SYNC-01 | 자료 버전 계약 보강 필요 | 파일 실패 주입, ACK 보류, 실제 상태 표시 관찰 |
| TC-03 | 업로드 실패 복구 | SAMPLE-03, SYNC-02, §4.6 | 일반 영속 재시도 미구현 | 가짜 시간, HTTP 응답 제어, 앱 재시작 |
| TC-04 | 삭제와 늦은 저장 | SAMPLE-04의 로컬 종류 저장 변형, PRIV-01 | 실제 코드 연결·통과(`qa/jvm`, 웹 시험장) | 실제 저장 직전 일시정지, 철회, 작업 재개, 파일 검사 |

이 네 개가 전체 QA는 아니다. 새 의심 등급, 추가 충돌 묶음, 보관 만료, 성능 측정, 원격 삭제 경합은 다음 시험으로 남긴다. TC-01의 수직 충격 감지 통과는 방지턱 분류 정확성의 통과가 아니다.

## TC-01 — 센서 보정과 음수 방향

- 테스트: `tc01_sensorThresholdAndSign()`.
- 시작: 각 행마다 중력 추정 상태가 없는 새 `ImpactSensor` 계산 경로. 에어백·속도 급감은 연결하지 않는다.
- 입력: t=0ms에 `(0, G, 0)`을 넣고, t=20ms에 아래 한 번의 펄스를 넣는다. G=9.80665f, 입력은 Float다.

| 행 | 두 번째 입력 | 예상 보정 g | 누적 onImpact 횟수 |
|---|---|---|---|
| A | `(0, G, 2.54G)` | 2.4892 | 0 |
| B | `(0, G, 2.56G)` | 2.5088 | 1 |
| C | `(0, G, -2.56G)` | 2.5088 | 1 |
| D | `(0, G+2.56G, 0)` | 2.5088 | 1 |

- 합격: 초기 입력 g=0/콜백 0회, 표의 모든 행에서 g 오차 ≤1e-5와 정확한 콜백 횟수·인자를 만족한다.
- 연결: [Crash.kt의 ImpactSensor.onSensorChanged](../../app/src/main/java/com/askthecar/Crash.kt). Android 이벤트 어댑터를 쓰거나 실제 계산을 공용 순수 함수로 최소 분리한다. 테스트 안에 계산식을 복제하지 않는다.
- 실패 로그: 행 이름, 원시값, 중력 추정 전후, 계산 g, 콜백 목록. 첫 행 실패 시 다음 행은 실행되지 않으므로 수정 후 네 행 전체를 다시 실행한다.

## TC-02 — 임시 자료 ACK를 완성본 ACK로 쓰지 않기

- 테스트: `tc02_previewAckDoesNotConfirmFinalDelivery()`.
- 공통 계정 `qa-driver-a`, 사고 t0=`1700000000.0`초. 가짜 경과시간 0ms의 epoch 기준이 t0다. 실제 현재 시각으로 이 자료를 만료시키지 않는다.
- 임시 자료: 같은 사고, 의미 버전 1, 진술 `qa-preview-v1`, 완성 기록 없음.
- 완성본: 같은 사고, 의미 버전 2, 진술 `qa-final-v2`, 필수 로그와 유효하게 계산한 지문 존재.
- `semanticVersion`은 시험 자료 구분용이다. 현재 서버의 변경 횟수 `version`이나 사고 시각 `seen`과 같다고 간주하지 않는다. 실제 저장 본문/지문과 대응시킨다. 어댑터만 버전 정책을 구현해 제품의 빈틈을 숨기지 않는다.

| 순서 | 실제 코드에 전달할 사건 | 합격 조건 |
|---|---|---|
| 1 | +1초에 임시 자료 업로드 200 → 폰 저장 → 폰 ACK를 차에 전달 | 폰 파일 진술은 preview, 카드 1개, 발행 ACK 1개 |
| 2 | +11초에 완성본 저장·업로드 200. 폰에는 아직 전달 안 함 | 차 저장·서버 접수 true, 완성본 폰 도착 false |
| 3 | 다음 폰 쓰기만 실패시키고 완성본 전달 | 폰 파일은 preview 유지, ACK 누적 1개, 완성본 도착 false |
| 4 | 동일 자료 재수신, 쓰기 성공, ACK 전달만 보류 | 폰 파일은 final, 카드 1개, ACK 누적 2개, 차의 완성본 도착 false |
| 5 | 보류한 완성본 ACK를 차에 전달 | 완성본 도착 true, 폰 카드 1개 |

- 연결: [CarSync.publish](../../app/src/main/java/com/askthecar/Handoff.kt) → [Sync.apply/save/ackSeen](../../phone/src/main/java/com/askthecar/phone/Sync.kt) → 차의 수신 상태 → [CarHome의 recStageOf/recStage](../../app/src/main/java/com/askthecar/CarHome.kt).
- ACK는 저장했다는 확인 메시지다. 네트워크 전송 계층은 제어할 수 있지만 ACK를 만들지 결정하는 앱 로직은 실제여야 한다. 시나리오에서는 ACK 전송 실패가 없고 전달만 보류하므로 누적 1/2회로 정확히 판정한다.
- `carShowsFinalArrived`는 실제 표시 상태에서 읽는다. `recStage`에 기대하는 Boolean을 직접 넣거나, `phoneStoredStatement == final`을 보고 어댑터가 차 표시를 계산하면 잘못된 시험이다.
- `publishFromCar`는 해당 시점의 로컬 파일·현재 사고를 준비하고 실제 발행 경로를 호출한다. 임시 자료에는 지문을 넣지 않고, 완성본에는 고정 합성 로그와 그 지문을 준비한다. 최종 로그 내용 자체는 이 케이스의 검증 범위가 아니다.
- 현재 두 앱은 별도의 application 모듈이다. `:phone`을 `:app`의 일반 JVM 라이브러리처럼 의존시키지 않는다. 동료가 실제 로직의 최소 분리 또는 두 앱을 연결하는 시험 어댑터 중 방식을 정한다.

## TC-03 — 실패 5초 후 재시도, 중간 재시작에도 유지

- 테스트: `tc03_retryAtFiveSecondsSurvivesRestart()`.
- 정책: `QA-PROPOSAL-01`. 온라인·동의 true·인증 유효. 가짜 스케줄러는 현재 실행 가능한 최초 업로드를 t=0에 실행한다. 최초 업로드에 허용한 실제 기기 2초 지연을 여기에는 섞지 않는다.
- 서버: 최초 요청은 지연 없이 503. 따라서 실패 확정 시각도 t=0이다.

| 가짜 시각 | 동작 | 합격 조건 |
|---|---|---|
| 0ms | 완성본 저장 → 실제 업로드 → 503 | 요청 누적 1개, 로컬 본문 유지, 큐 1개, 서버 성공 false |
| 2000ms | 앱 메모리와 작업 실행기를 재생성 | 디스크·시각·외부 요청 기록 유지. 재시도 예정은 5000ms 그대로 |
| 2000ms 이후 | 서버 응답을 200으로 변경 | 온라인 상태는 그대로. 연결 복구 이벤트는 보내지 않음 |
| 4999ms | 가짜 시계 진행 | 요청 누적 1개 |
| 5000ms | 가짜 시계 진행 | 요청 누적 2개, 시각 `[0, 5000]`, 서버 카드 1개, 큐 0개 |
| 20000ms | 다음 실패 때 예약됐을 법한 시각까지 진행 | 성공한 버전의 요청은 여전히 총 2개 |

- 모든 요청에서 계정·사고·버전·본문이 같고 로컬 파일도 유지돼야 한다. 서버 성공 뒤에도 폰 ACK를 주지 않았으므로 폰 도착 false다.
- 연결: [CarSync.publish/submit](../../app/src/main/java/com/askthecar/Handoff.kt), 향후 영속 전송 큐·스케줄러. 서버는 대체 가능하지만 **재시도를 예약하고 복구하는 부분은 실제 제품 로직**이어야 한다.
- 기존 코드에는 일반 업로드의 영속 재시도가 없다. 테스트 시스템은 만들어도 제품 보강 전에는 이 제안 기준을 통과하지 못할 수 있다. 가짜 스케줄러가 자체적으로 HTTP 요청을 만들어내면 잘못된 시험이다.
- `restartApp()`은 생성자만 다시 부르고 옛 스레드를 살려 두는 방식이 아니다. 이전 작업을 종료하고 디스크에서 복구해야 한다. HTTP 요청 관찰 기록은 시험 장치 쪽에 남긴다. 이 시험의 재시작은 네트워크 복구 이벤트를 별도로 발생시키지 않는다.

## TC-04 — 동의 철회 뒤 늦은 종류 저장이 사고를 되살리지 않기

- 테스트: `tc04_withdrawalPreventsLateKindWriteResurrection()`.
- 시작: DRIVE 동의 true, 사고 A의 실제 폴더·로그·카드 1개.
- 지연할 작업: [CrashFlow.chooseKind](../../app/src/main/java/com/askthecar/Crash.kt)의 OBJECT 선택으로 생긴 종류 저장 스레드. 해당 스레드가 기존 폴더 참조 `d`를 잡은 뒤 디스크에 처음 닿기 **직전**에서 멈춘다.
- 앱 동작: 종류 저장은 [`Records.write`](../../app/src/main/java/com/askthecar/Consent.kt)를 거친다. 삭제와 같은 잠금 안에서 DRIVE 동의와 지금 사고 폴더를 다시 확인하고, 지운 폴더는 다시 만들지 않는다. 그래서 재개된 작업은 아무것도 쓰지 않고 끝난다.

| 순서 | 동작 | 합격 조건 |
|---|---|---|
| 1 | 실제 종류 저장 작업을 정지 지점까지 진행 | 정지 지점 도달 확인, 작업 미완료 |
| 2 | 실제 DRIVE 동의 철회 호출 | 동의 false, 사고 폴더/파일 없음, 카드 0개, 현재 사고 null |
| 3 | 보류한 작업을 재개하고 완료까지 진행 | 작업 완료 확인. 폴더/파일/카드/현재 사고는 여전히 없음 |
| 4 | 앱 재시작 | 동의 false, 삭제한 사고가 로딩되지 않음 |

- 연결: [Consent.set/deleteRecords](../../app/src/main/java/com/askthecar/Consent.kt)와 실제 종류 저장 경로. 어댑터가 대신 폴더를 지우거나 늦은 저장을 차단하면 안 된다.
- barrier는 시험이 풀어 줄 때까지 특정 작업을 멈추는 장치다. 처음 작업이 그 위치에 도달했다는 증거를 남긴다. 마지막 확인 전에 스레드를 강제 취소해서 통과시키지 않는다.
- `runReady()`는 이 보류 작업을 기다리며 교착되면 안 된다. 재개 이후 대기는 실제 스레드라면 최대 5초로 제한한다. 미완료는 시험 인프라 중단으로 기록한다.
- 이 샘플은 **로컬 파일 재생성 경합**에 집중한다. 네트워크는 성공하는 통제된 환경으로 두며, 원격 삭제 성공·폰 삭제·늦은 업로드 방어까지 통과했다고 해석하지 않는다. 해당 변형은 상위 명세 SAMPLE-04에 남아 있다.

## 동료가 시스템을 구축하는 순서

1. TC-01용 어댑터부터 구현한다. 파일·네트워크 없이 입력 전달·실제 콜백·실패 보고의 기본 연결을 확인한다.
2. 가짜 시계와 제어 가능한 작업 실행기를 만들고 TC-03을 연결한다. 제품 재시도 미구현과 어댑터 미연결을 구분해 보고한다.
3. TC-02에 저장 실패·ACK 보류·실제 표시 상태 읽기를 연결한다.
4. TC-04에 실제 저장 직전 정지 지점을 연결한다. 각 시험 종료 시 파일·스레드·싱글턴을 정리한다.

각 어댑터 메서드는 현재 앱 함수가 아닌 시험용 계약이다. 필요한 제어 지점이 없으면 최소 분리 작업을 명시한다. 제품 기능을 고쳐야 하는 작업은 그와 별도 변경으로 관리한다. 관찰 불가 상태를 0·false로 채워 넣지 말고 연결 실패로 보고한다.

## 실행 연결 방법

현재 `qa/samples`는 Gradle source set 밖에 있다. 어댑터 연결 뒤 동료가 선택한 테스트 모듈의 `src/test/java/com/askthecar/qa/samples/`로 세 Kotlin 파일을 옮기거나, 해당 모듈의 test source set에 이 디렉터리를 등록한다. 두 곳에 동시에 복사/등록하지 않는다.

기존 앱 모듈에는 JUnit 4.13.2가 선언돼 있다. 예를 들어 실제 연결을 `:app`의 로컬 테스트에 구성했다면 다음처럼 실행한다. 두 앱 통합에 기기 시험이 필요하면 그 환경의 실행 명령을 인수인계에 추가한다.

```sh
# 아래 명령은 :app 테스트 소스 등록과 실제 어댑터 연결 이후에 사용한다.
sh ./gradlew :app:testDebugUnitTest --tests 'com.askthecar.qa.samples.QaSampleTest'

# 첫 케이스만 실행
sh ./gradlew :app:testDebugUnitTest --tests 'com.askthecar.qa.samples.QaSampleTest.tc01_sensorThresholdAndSign'
```

Windows에서는 `tools\run.cmd .\gradlew.bat` 뒤에 같은 task와 `--tests`를 붙인다. 등록 전 실행은 테스트를 찾지 못하며, 등록만 하고 어댑터를 연결하지 않으면 네 케이스가 `BLOCKED_ADAPTER`로 실패하는 것이 정상이다. JDK·Android SDK·의존성 준비는 별도다.

## 결과 기록

각 케이스에 다음을 남긴다: `TC ID / 요구사항 ID / 제품 커밋 / 정책 설정 / 실제 연결한 함수 / 입력 / 기대값 / 실제값 / 파일·요청·화면 근거 / 실행 상태`.

- `BLOCKED_ADAPTER`: 실제 제품 연결 전. 제품 버그나 통과로 집계하지 않음.
- `BLOCKED_ENVIRONMENT`: SDK·기기·빌드·시험 시간 제어 실패. 기능 판정 불가.
- `FAIL_REQUIREMENT`: 실제 경로를 실행했으나 기대값 불일치. 기존 동작의 회귀와 제안된 기능 미구현을 구분.
- `PASS`: 해당 케이스의 실제 경로와 모든 판정 통과. 전체 제품 QA 통과를 뜻하지 않음.

### 검증 기록

- 2026-11-12: 앱 연결 경로를 코드와 대조. Kotlin 2.0.21, JVM target 17로 세 Kotlin 파일의 독립 컴파일 성공. 로컬 캐시의 도구를 이용했으며 저장소 Gradle 설정은 변경하지 않았다.
- JUnit 4.13.2 실행에서 4개 발견, 4개 모두 `BLOCKED_ADAPTER` 실패 확인. 이는 연결 전 차단 확인이며 기능 테스트 통과가 아니다. 실제 앱 연결·Android 빌드·게임·성능 시험은 실행하지 않았다.
