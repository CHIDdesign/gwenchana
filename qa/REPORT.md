# QA 최종 보고 (2026-11-15)

대상: 차 앱 사고 감지·기록 저장 코드. 기준: 공개본 main `5ffe61e`(심사용 APK와 같은 코드)와 이 브랜치(`qa/tester-and-fixes`, PR #3).

## 1. 무엇이 문제였나

1. **에어백 신호를 버리는 경우가 있었다.** 앱을 켠 지 1분 안에 충격으로 사고를 먼저 잡으면, 곧이어 에어백이 터져도 큰 사고로 올라가지 않았다. "사고가 아니에요"를 누른 직후, 또는 저장 대기(10초)가 끝난 뒤에 온 에어백도 버렸다. 원래 뜻은 "앱이 다시 켜졌을 때 이미 터져 있던 에어백 값을 새 사고로 착각하지 않기"였는데, 앱이 지켜보던 중에 생긴 에어백까지 막고 있었다.
2. **동의를 철회해 지운 사고가 되살아날 수 있었다.** 사고 종류 기록(`kind.txt`) 작업이 폴더를 잡고 있다가 삭제 뒤에 실행되면, 지운 사고 폴더를 다시 만들었다. 사진 복사와 충돌 전 저장도 같은 위험이 있었다.

## 2. 무엇을 바꿨나 (코드)

에어백 조건 (`Crash.kt`, CrashWatcher):

```kotlin
// 이번 실행에서 이미 사고를 감지했다면 그 뒤의 에어백은 언제든 받는다.
// 60초 억제는 이번 실행에서 아직 사고가 없을 때만(재시작 뒤 늦게 온 값).
s.airbag && !prev.airbag && s.t - started > 3 &&
    (seenThisRun || s.t - started > REPEAT_SEC || s.t - lastIncidentT() > REPEAT_SEC) ->
        trigger("에어백 전개", severe = true)
```

사고 폴더 쓰기와 삭제의 잠금 (`Consent.kt`):

```kotlin
object Records {
    private val lock = Any()
    fun <T> write(dir: File, block: () -> T): T? = synchronized(lock) {
        if (!Consent.allowed(Consent.Item.DRIVE)) return null          // 동의가 꺼졌으면 안 쓴다
        if (!dir.isDirectory && (CrashFlow.dir != dir || !(dir.mkdirs() || dir.isDirectory))) return null
        block()                                                          // 지운 폴더는 다시 만들지 않는다
    }
    fun deleting(block: () -> Unit) = synchronized(lock, block)
}
```

- `Consent.deleteRecords`는 `Records.deleting { CrashFlow.dir = null; 폴더 삭제 }`로 같은 잠금 안에서 지운다.
- 종류 기록, 충돌 전 저장, 최종 저장, 경위서, 사진 복사, 영상 끝 시각은 모두 `Records.write`로 쓴다.
- 감지 중에 삭제가 끝나면 그 사고를 다시 띄우지 않는다. 운전자가 고른 종류는 추정이 덮지 않고, 마지막 선택만 저장한다.

## 3. 왜 앱이 그대로 동작한다고 보나

- **바뀐 곳이 좁다.** 차 앱 두 파일만 바꿨다. 화면, 휴대폰 앱, 서버, 저장 형식, 권한, 라이브러리는 그대로다.
- **평소 흐름에서는 하는 일이 같다.** 사고 기록 서비스는 주행 기록 동의가 있을 때만 돌고, 지금 사고의 폴더는 `CrashFlow.dir`와 같다. 그래서 `Records.write`는 예전처럼 폴더를 만들고 쓴다. 지워졌거나 동의가 꺼졌을 때만 달라진다.
- **잠금이 앱을 멈추게 하지 않는다.** 잠금 안에서는 짧은 파일 쓰기만 한다. 네트워크, 화면 상태, 다른 잠금은 잠금 밖이다(큰 영상 파일의 지문도 밖에서 계산). 삭제는 화면 스레드에서 몇 ms만 기다린다.
- **에어백 규칙은 넓어지기만 했다.** 켠 지 1분이 지난 뒤의 동작은 그대로이고(대조 시험 통과), 재시작 직후 이미 터져 있던 값을 막는 보호도 그대로다.
- **같은 시험으로 앞뒤를 비교했다.** 실제 Kotlin 소스를 그대로 컴파일하는 JVM 시험대와 웹 시험장 모두, 고치기 전에는 실패하고 고친 뒤에는 통과한다. 이전에 통과하던 시험은 고친 뒤에도 모두 통과한다.

## 4. 시험 결과

- **삭제 경합(TC-04):** 공개본에서는 동의를 철회한 뒤 늦게 끝난 종류 기록이 지운 사고 폴더를 되살렸다. 수정본에서는 폴더가 지워진 채로 남고, 앱을 다시 켜도 나타나지 않는다.
- **에어백(DRV-12, 12b, 12c):** 공개본에서는 켠 직후 충격 뒤 에어백, "사고가 아니에요" 직후 에어백, 저장 대기가 끝난 뒤 에어백이 모두 큰 사고로 기록되지 않았다. 수정본에서는 셋 다 큰 사고로 기록된다.
- **바뀌지 않아야 할 것:** 센서 보정·2.5g 기준(TC-01)과 켠 지 1분 뒤 에어백(대조 시험)은 두 버전 모두 통과한다. 정면·뒤·옆·후진·급제동·지그재그·과속방지턱·고속도로·벽 스침 자동 운전 시험도 두 버전 모두 같은 결과로 통과한다.
- **아직 실패하는 것:** 임시 자료 저장 확인을 완성본 확인으로 쓰지 않기(TC-02)와 업로드 실패 5초 뒤 재시도(TC-03)는 명세의 보강 제안 기능이 앱에 아직 없어서 두 버전 모두 실패한다. 실제 코드 시험대에서는 연결할 기능이 없어 "연결 전"으로 표시한다.

숫자: 웹 시험장 16개 중 공개본 12, 수정본 14 통과. JVM 시험대 9개 중 공개본 통과 2·실패 5·연결 전 2, 수정본 통과 7·실패 0·연결 전 2. 자세한 줄별 결과는 [`jvm/README.md`](jvm/README.md).

## 5. 확인하지 못한 것 (미확인)

- Android Gradle 빌드(AGP 8.8.2, Kotlin 2.1.21)와 기존 단위 테스트 65개. 작업 환경에 Android SDK가 없었다. 바뀐 두 파일은 Kotlin 2.0.21로 실제 소스와 함께 컴파일·실행했다.
- 에뮬레이터·실차에서의 동작, `apk/`의 APK 다시 빌드.
