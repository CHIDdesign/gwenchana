감지 흐름: 신호에서 저장된 기록까지

How a crash becomes an incident, a saved 40-second record and a fingerprint. Read sections 2 to 5, then we go through the questions in section 9 together. When something looks wrong, name the section and the line.

요약

  • 이 부분은 차 신호를 받아 사고를 잡고(경로 4가지), 사고를 만들고, 10초 뒤 앞 30초와 뒤 10초를 저장해 SHA-256 지문을 남겨요. 핵심은 Crash.kt의 ImpactSensor와 CrashWatcher, 그리고 사고 폴더 쓰기를 맡는 Consent.kt의 Records예요.
  • 확인하고 고친 문제 (F-01): 앱을 켠 지 60초 안에는 충격으로 먼저 잡힌 사고에 에어백 신호가 와도 큰 사고로 올라가지 않았어요. 이제는 저장 대기 중인 사고가 있으면, 켠 지 얼마가 지났든 에어백 신호가 그 사고를 큰 사고로 올려요(396행). 명세 DET-04대로예요.
  • 지운 폴더를 다시 만드는 문제도 고침 (TC-04·S-01·S-02): 동의를 철회해 사고 폴더를 지운 뒤, 늦게 끝나는 저장 작업이 폴더를 다시 만들 수 있었어요. 이제 사고 폴더 쓰기는 모두 삭제와 같은 잠금(Records.write)을 거치고, 폴더는 지금 사고의 폴더일 때만 만들어요. 지운 사고에는 아무것도 쓰지 않아요.
  • 시험: 웹 시험장(Node·실제 브라우저)에서 공개본 5ffe61e는 TC-04·DRV-12가 실패하고, 수정본은 둘 다 통과해요. 사진 복사·충돌 전 저장은 코드 리뷰로 확인했어요. Kotlin 쪽은 qa/jvm (실제 Kotlin 코드)을 마무리하고 있어요.
  • 빈틈: 속도 급감 경로가 먼저 잡는 시험이 없어요. 스레드 경합은 웹 모델로 재현할 수 없어요. 센서 축 부호는 웹이 앱 규칙에 맞춰 넣기 때문에 틀려도 못 잡아요.
  • 같이 볼 질문 8개는 9장에 있어요. 그중 2개(에어백 규칙, 폴더 쓰기 확인)는 정했어요.

2 Four ways a crash is detected

Every path ends in the same trigger(). If an incident is already waiting to be saved, trigger() only raises it to severe (and only when the new signal is the airbag). Otherwise it starts a new incident.

3 One incident over time

Five threads touch the same incident within about 12 seconds. The marked writes are where a late job used to recreate a folder that the driver had just deleted by withdrawing consent. They now all go through Records.write, which shares one lock with the deletion.

Line 396: the airbag condition now starts with pendingSince != null ||. The 60 s rule (s.t - started > REPEAT_SEC || s.t - lastIncidentT() > REPEAT_SEC) applies only when nothing is waiting, so an app that restarts within a minute of a saved incident still does not treat the old airbag value as a new crash. write() runs block under the lock and returns its result. It returns null and writes nothing when DRIVE consent is off, or when the folder is missing and is not CrashFlow.dir (the current incident). deleteRecords clears CrashFlow.dir and deletes the folders inside Records.deleting { }, under the same lock, so a late write either lands before the deletion or finds its incident gone and writes nothing. Only short file writes run inside the lock; relay calls, photo analysis and the video save stay outside.

6 Findings and gaps

Status words: fixed = shown or suspected on 5ffe61e, fixed on qa/tester-and-fixes; gap = nothing tests it.

F-01 · Crash.kt 396fixed

Airbag after impact always upgrades the waiting incident

The airbag condition checks for a waiting incident first (pendingSince != null ||). An airbag edge more than 3 s after start now always makes the waiting incident severe, so "사고가 아니에요" goes away and the guide starts with "차로 오는 전화를 받아 주세요" (the car's rescue-center call). The 60 s repeat rule applies only when nothing is waiting.

Was: in the first 60 s the repeat rule counted the incident the impact path had just created as "the last incident", so the airbag was dropped. Tests: DRV-12 fails on 5ffe61e and passes on the fixed code; DRV-01, DRV-10 still pass. Matches spec DET-04. Kotlin: qa/jvm (실제 Kotlin 코드).

S-01 · Crash.kt 543–545fixed

The photo copy runs only inside Records.write

copyTo creates missing parent folders, so the copy and camera.sha256 now run inside Records.write. If the incident was deleted, nothing is copied and the folder stays gone; the cached shot is deleted either way. Same promise as TC-04 (PRIV-01).

Evidence: code review plus the library check in section 4. The web copy has no photo copy, so no web case covers it.

S-02 · Crash.kt 428–439fixed

Pre-save creates the folder only for the current incident

trigger() sets CrashFlow.dir before it starts the pre-save thread, and the thread writes inside Records.write. After a deletion, which clears CrashFlow.dir under the same lock, the pre-save writes nothing. The one shared lock covers S-01, S-02 and TC-04.

Evidence: code review. Was theoretical (a person cannot withdraw consent within milliseconds of a crash), but would matter if deletion ever became automatic or remote.

G-01 · pathsgap

No case makes path C the first detector

In every DRV case path A fires first. A soft, long impact (peak between 1.5 and 2.5 g, 15 km/h lost in 0.3 s) would exercise C alone.

Proposal: DRV-13 "soft barrier".

G-02 · threadsgap

Races cannot be shown by the web model

The app runs the sensor thread, the recorder thread, the report thread and the UI at the same time over shared state. The web copy runs them one at a time, so it can only show a race where we add a pause point.

The Records lock was checked by code review; races belong in qa/jvm (실제 Kotlin 코드).

G-03 · sensor axesgap

Axis signs are unverified, and the web cannot catch a wrong sign

RIGHT_SIGN and FORWARD_SIGN are marked 미확인 in the code. The simulator feeds values in the app's own convention, so a sign error would still pass every case and show the wrong side on screen.

Needs one BeamNG run per side, or a measurement in a real car.

9 Questions to go through together

  1. decided An airbag signal always makes the waiting incident severe, even inside the first 60 s.The spec says so too. We chose option (a), checking for a waiting incident before the repeat rule (line 396), because it is the smallest change: one added condition, and the 60 s rule still guards the app-restart case it was written for whenever nothing is waiting. Not taken: (b) compare against the last saved incident; (c) treat the first airbag value after start as a baseline.
  2. A second hit 10 or more seconds after the first starts a brand-new incident and resets the guide to the first question. Is that acceptable?Example: stopped on a highway, rear-ended 15 s later while walking through the evacuation steps. Spec DET-04 says the current repeat rule is not permanent; section 4.5 proposes grouping hits into one incident.
  3. decided Every job that writes into a crash folder checks again under one shared lock.Records (Consent.kt 17–28) is used by every save-path writer and by Consent.deleteRecords, so a late write either lands before the deletion or finds its incident gone and writes nothing. It closed TC-04, S-01 and S-02 together; a single storage queue that also runs the deletion was not needed.
  4. Is detecting a 40 km/h speed bump acceptable for now?The 2.5 g threshold uses all three axes, so vertical jolts count (DRV-08). Spec 4.4 proposes a "suspect impact" tier.
  5. Does path C catch any real crash that path A misses?If yes, we need DRV-13 to prove it. If no, path C only adds false-positive risk from speed glitches.
  6. Who can confirm the accelerometer axis signs (G-03)?A wrong sign shows the impact on the wrong side of the car, in the photo guide, and in the facts sent to the phone.
  7. Does the road speed limit arrive when no route is set in the car's navigation?The team's notes say unverified. Without it, "highway" falls back to a 30 s average speed of 80 km/h or more, and the guide asks the driver.
  8. When finish() throws, is the driver ever told?saveFailed is set (line 402), and the strip shows "기록 저장에 실패했어요". Nothing tests it. If the failure comes before the new log.json replaces the old one, the folder keeps only the pre-save file (the 30 s before the crash). Spec REC-02 covers this case.
