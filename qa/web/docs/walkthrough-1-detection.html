요약

  • 이 부분은 차 신호를 받아 사고를 잡고(경로 4가지), 사고를 만들고, 10초 뒤 앞 30초와 뒤 10초를 저장해 SHA-256 지문을 남겨요. 핵심은 Crash.kt의 ImpactSensor와 CrashWatcher, 그리고 사고 폴더 쓰기를 맡는 Consent.kt의 Records예요.
  • 확인하고 고친 문제 (F-01): 앱을 켠 지 60초 안에는 충격으로 먼저 잡힌 사고 뒤에 온 에어백 신호가 버려졌어요. 이제는 이번 실행에서 사고를 한 번이라도 감지했으면 그 뒤의 에어백은 언제든 받아요(407행 seenThisRun). 저장 대기 중이면 그 사고를 큰 사고로 올리고, 대기가 끝났거나 "사고가 아니에요"로 닫은 뒤면 새 큰 사고로 기록해요. 60초 억제는 이번 실행에서 아직 사고가 없을 때만 남아요(앱이 다시 켜진 뒤 이미 터져 있던 에어백 값이 늦게 온 경우). 명세 DET-04대로예요.
  • 지운 폴더를 다시 만드는 문제도 고침 (TC-04·S-01·S-02): 동의를 철회해 사고 폴더를 지운 뒤, 늦게 끝나는 저장 작업이 폴더를 다시 만들 수 있었어요. 이제 사고 폴더 쓰기는 모두 삭제와 같은 잠금(Records.write)을 거치고, 폴더는 지금 사고의 폴더일 때만 만들어요. 지운 사고에는 아무것도 쓰지 않아요. 사고를 감지하는 도중에 삭제가 끝나면 그 사고를 화면에 띄우지 않아요(477행).
  • 사고 종류 기록 순서도 정리: 운전자가 고른 종류는 나중에 들어온 추정이 덮지 않고(chooseKind() 102행), kind.txt에는 사고 폴더마다 마지막으로 고른 값만 남아요(kindSeq).
  • 시험: 실제 Kotlin 코드를 JVM에서 돌리는 qa/jvm 시험대에서 공개본 5ffe61e는 TC-04·DRV-12·DRV-12b("사고가 아니에요" 바로 뒤 에어백)·DRV-12c(충격 11.5초 뒤, 저장 대기가 끝난 뒤 에어백)가 모두 실패하고, 수정본은 모두 통과해요. 웹 시험장(Node·실제 브라우저)도 TC-04·DRV-12에서 같은 결과예요. 사진 복사·충돌 전 저장·감지 중 삭제는 코드 리뷰로만 확인했어요. Android 빌드·에뮬레이터 확인은 아직이에요.
  • 빈틈: 속도 급감 경로가 먼저 잡는 시험이 없어요. 재시작 직후 이미 터져 있던 에어백(60초 억제가 남은 유일한 경우)을 시험하는 케이스도 없어요. 스레드 경합은 웹 모델로 재현할 수 없고, qa/jvm도 종류 기록(TC-04) 하나만 실제 스레드를 멈춰 봐요. 센서 축 부호는 웹이 앱 규칙에 맞춰 넣기 때문에 틀려도 못 잡아요.
  • 같이 볼 질문 8개는 9장에 있어요. 그중 2개(에어백 규칙, 폴더 쓰기 확인)는 정했어요.

2 Four ways a crash is detected

Every path ends in the same trigger(). If an incident is waiting to be saved and is still open, trigger() only raises it to severe (and only when the new signal is the airbag). Otherwise, including after "사고가 아니에요", it starts a new incident.

3 One incident over time

Five threads touch the same incident within about 12 seconds. The marked writes are where a late job used to recreate a folder that the driver had just deleted by withdrawing consent. They now all go through Records.write, which shares one lock with the deletion.

6 Findings and gaps

Status words: fixed = shown or suspected on 5ffe61e, fixed on qa/tester-and-fixes; gap = nothing tests it.

F-01 · Crash.kt 407fixed

After the first incident of a run, an airbag edge is never dropped

The airbag condition starts with seenThisRun ||, a flag trigger() sets on every new incident. Once this run has detected anything, an airbag edge more than 3 s after start always reaches trigger(). A waiting incident becomes severe, so "사고가 아니에요" goes away and the guide starts with "차로 오는 전화를 받아 주세요" (the car's rescue-center call). After the save window, or after the driver closed the incident with "사고가 아니에요", it becomes a new severe incident. The 60 s repeat rule applies only before the first incident of a run: an airbag that was already on and arrives late after an app restart.

Was: in the first 60 s the repeat rule counted the incident the impact path had just created as "the last incident", so the airbag was dropped. Tests (qa/jvm, real Kotlin): DRV-12 (airbag 0.5 s after the impact), DRV-12b (right after "사고가 아니에요") and DRV-12c (11.5 s after the impact) fail on 5ffe61e and pass on the branch; the web DRV-12 the same; DRV-01, DRV-10 and the 65 s control pass on both. Matches spec DET-04 and §4.5.

S-01 · Crash.kt 562–564fixed

The photo copy runs only inside Records.write

copyTo creates missing parent folders, so the copy and camera.sha256 now run inside Records.write. If the incident was deleted, nothing is copied and the folder stays gone; the cached shot is deleted either way. Same promise as TC-04 (PRIV-01).

Evidence: code review plus the library check in section 4. The web copy has no photo copy, so no web case covers it.

S-02 · Crash.kt 440–451, 477fixed

Pre-save creates the folder only for the current incident

trigger() sets CrashFlow.dir before it starts the pre-save thread, and the thread writes inside Records.write. After a deletion, which clears CrashFlow.dir under the same lock, the pre-save writes nothing. If the deletion lands while trigger() is still setting up, trigger() also drops the incident before its screen opens (477). The one shared lock covers S-01, S-02 and TC-04.

Evidence: code review. Was theoretical (a person cannot withdraw consent within milliseconds of a crash), but would matter if deletion ever became automatic or remote.

G-01 · pathsgap

No case makes path C the first detector

In every DRV case path A fires first. A soft, long impact (peak between 1.5 and 2.5 g, 15 km/h lost in 0.3 s) would exercise C alone.

Proposal: DRV-13 "soft barrier".

G-02 · threadsgap

Races cannot be shown by the web model

The app runs the sensor thread, the recorder thread, the report thread and the UI at the same time over shared state. The web copy runs them one at a time, so it can only show a race where we add a pause point.

qa/jvm (real Kotlin, real threads) pauses one race on purpose: TC-04 holds the kind-write thread at its first disk call while consent is withdrawn. The other writers, the trigger() deletion check and the kindSeq ordering are checked by code review only.

G-03 · sensor axesgap

Axis signs are unverified, and the web cannot catch a wrong sign

RIGHT_SIGN and FORWARD_SIGN are marked 미확인 in the code. The simulator feeds values in the app's own convention, so a sign error would still pass every case and show the wrong side on screen.

Needs one BeamNG run per side, or a measurement in a real car.

9 Questions to go through together

  1. decided Once a run has detected an incident, an airbag signal is never dropped, even inside the first 60 s. The 60 s suppression applies only before the first incident of a run.The spec says so too (DET-04; §4.5: a new airbag deployment is not suppressed). Our first choice, (a) a check for a waiting incident, covered only the 10 s wait, so an airbag after the save window was still dropped in the first 60 s (DRV-12c). The final rule is a per-run flag, seenThisRun (line 407, set in trigger() at 434): an airbag edge after the first incident turned on while the app was watching, so it is accepted at any time. It also covers an airbag right after "사고가 아니에요" (DRV-12b). The 60 s rule now guards only the case it was written for: before anything has been detected, an airbag value that was already on arrives late after an app restart. Not taken: (b) compare against the last saved incident; (c) treat the first airbag value after start as a baseline.
  2. A second hit 10 or more seconds after the first starts a brand-new incident and resets the guide to the first question. Is that acceptable?Example: stopped on a highway, rear-ended 15 s later while walking through the evacuation steps. Spec DET-04 says the current repeat rule is not permanent; section 4.5 proposes grouping hits into one incident. Since the airbag change, an airbag that deploys after the save window does the same: it starts a new severe incident (DRV-12c).
  3. decided Every job that writes into a crash folder checks again under one shared lock.Records (Consent.kt 17–28) is used by every save-path writer and by Consent.deleteRecords, so a late write either lands before the deletion or finds its incident gone and writes nothing. It closed TC-04, S-01 and S-02 together; a single storage queue that also runs the deletion was not needed.
  4. Is detecting a 40 km/h speed bump acceptable for now?The 2.5 g threshold uses all three axes, so vertical jolts count (DRV-08). Spec 4.4 proposes a "suspect impact" tier.
  5. Does path C catch any real crash that path A misses?If yes, we need DRV-13 to prove it. If no, path C only adds false-positive risk from speed glitches.
  6. Who can confirm the accelerometer axis signs (G-03)?A wrong sign shows the impact on the wrong side of the car, in the photo guide, and in the facts sent to the phone.
  7. Does the road speed limit arrive when no route is set in the car's navigation?The team's notes say unverified. Without it, "highway" falls back to a 30 s average speed of 80 km/h or more, and the guide asks the driver.
  8. When finish() throws, is the driver ever told?saveFailed is set (line 413), and the strip shows "기록 저장에 실패했어요". Nothing tests it. If the failure comes before the new log.json replaces the old one, the folder keeps only the pre-save file (the 30 s before the crash). Spec REC-02 covers this case.
