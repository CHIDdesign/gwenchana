## 1. 문서 사용법과 근거

### 1.1 요구사항 표기

각 요구사항에는 ID, 요구 근거, 현재 구현 상태를 표시한다. 구현 상태는 실행 통과 여부가 아니다.

| 근거 표기 | 의미 | 테스트 처리 |
|---|---|---|
| 기준 | 현재 제품 설명·원칙·코드에 근거한 검증 기준 초안 | 기준선 시험에 포함하고 실제 결과를 기록 |
| 보강 제안 | 기존 약속의 빈틈을 줄이기 위해 제안하는 요구 | 팀 채택 여부를 기록한 뒤 필수 통과 기준으로 승격 |
| 향후 기획 | 기획 문서에는 있으나 현재 MVP에 전부 들어 있지 않은 동작 | 대상 버전을 정하고 별도 시험 목록으로 관리 |
| 결정 필요 | 문서 충돌 또는 수치·동작 정책 미정 | 기대값 미정으로 기록. 임의의 값으로 성공·실패 판정 금지 |

구현 상태: `구현됨 / 일부 구현 / 구현 경로 미확인 / 미구현 / 정책 미정`.

검증 상태는 별도 열로 관리한다: `테스트 정의만 / 기존 테스트 존재 / 실행 통과 / 실행 실패 / 환경 때문에 미검증 / 기대값 미정`.

미구현 요구의 시험이 실패하더라도 곧바로 현재 MVP의 회귀 버그라는 뜻은 아니다. 제안 채택 상태와 대상 버전을 함께 본다. 반대로 미구현 시험을 실행하지 않았거나 예상 실패로 표시했다고 전체 제품 품질을 통과로 보고하지 않는다.

### 1.2 근거 문서와 해석 순서

- [README](../../README.md): 현재 공개 기능 설명과 시제품 제한.

- [앱 전체 흐름 기획](<../reports/앱 전체 흐름 기획.md>): 향후 기능·분기·화면·보관 제안. 같은 문서 안에도 채택 표기와 결정 대기 표기가 섞여 있다.
- [기획서](../기획서.md), [초기 개발 계획](../PLAN.md): 제품 의도와 과거 계획. 오래된 API·흐름을 현재 동작으로 간주하지 않는다.

충돌 시에는 **현재 구현 / 현재 사용자 안내 / 향후 기획**을 각각 적고 결정 항목을 만든다. 이 문서는 의료·법률·공식 사고 대응 수칙을 새로 정하는 문서가 아니다. 안내 내용의 전문적 타당성은 별도 검토 대상으로 남긴다.

## 2. 용어·상태·관찰 기준

### 2.1 용어와 단위

| 용어 | 정의 |
|---|---|
| 원시 가속도 | 센서에서 들어온 축별 값. 단위는 m/s². 중력 성분을 포함한다. |
| 보정된 충격값 | 현재 중력 추정치를 뺀 세 축의 크기를 중력가속도 G로 나눈 값. 단위는 g. |
| G | 앱 계산에 쓰는 `SensorManager.GRAVITY_EARTH`. 시험도 같은 상수값을 사용한다. 브리지의 9.81과 혼용하지 않는다. |
| 사고 시각 t0 | 사고 식별과 기록 구간 기준으로 쓰는 시각. 현재 데이터 모델은 epoch 초를 `Double`로 전달한다. |
| 임시 자료 | 사고 직후 아직 후속 10초의 기록과 보고서가 준비되지 않은 자료. |
| 완성본 | 시험에서 명시한 필수 자료가 저장된 버전. 선택적 AI 처리·사진 유무와 별도로 정의한다. |
| 서버 접수 | 서버가 해당 업로드에 성공 응답한 상태. 휴대폰 수신을 뜻하지 않는다. |
| 휴대폰 도착 | 대상 휴대폰이 해당 사고의 해당 자료 버전을 저장하고 확인한 상태라는 목표 정의. |
| 오탐 / 미탐 | 사고가 아닌데 감지 / 시험에서 감지해야 한다고 정한 사고를 놓침. 근거가 불명확하면 판정 보류. |
| 무효화 세대 | 삭제·로그아웃 등 이후 이전 작업을 구분하기 위한 개념. 현재 코드의 필드명이나 구현 방식을 지정하는 것은 아니다. |

경과시간 시험과 달력·보관기간 시험을 분리한다. 시스템 시계가 바뀌어도 지연 작업의 순서가 뒤집히지 않는지는 보강 검증 대상이다. 시각 비교의 허용오차는 각 테스트에 명시하며, UI의 반올림된 숫자로 경계값을 판정하지 않는다.

### 2.2 사고 진행 상태와 자료 전달 상태를 분리

사고 처리와 자료 전달은 동시에 진행될 수 있다. 한 개의 `완료` 값으로 합치지 않는다.

- 사고 흐름: 대기 → 감지 → 응답·안내 → 후속 관리. `사고 아님`, `다시 열기`, `삭제`는 각각 별도 전환이다.
- 기록 흐름: 메모리 기록 → 사고 전 구간 저장 → 후속 구간 수집 → 필수 자료 저장 성공/실패.
- 전달 흐름: 전송 대기 → 서버 접수 → 휴대폰 저장 확인. 네트워크 실패로 로컬 사고 기록을 지우지 않는다.
- 공유 흐름: 문서 생성 → 공유 창 열기 → 사용자의 보냈다는 표시. 보험사 수신·접수 완료는 별도의 사실이다.

이는 명세용 상태 구분이다. 현재 구현의 enum과 일대일로 같다는 뜻이 아니다.

### 2.3 공통 관찰값

시험 결과에는 사고 ID·계정, 자료 버전 또는 동등한 식별 정보, 입력 시각, 감지 이유, 파일 목록, 요청·응답 순서, 화면 상태를 남긴다. 현재 저장소에 자료 버전 필드는 없으므로 필요한 시험에서는 테스트용 의미 표기로 구분한다.

- 개인정보·키·실제 진술 원문 대신 고정된 합성 데이터를 사용한다.
- 게임 시험은 원본 가속도 / 합성 에어백 / 합성 펄스 / 앱 계산값을 구분한다.
- 사진·AI·3D 같은 선택 기능이 실패해도 기본 기록의 성공 여부는 독립적으로 관찰한다.
- 파일 생성 시도, 메모리 상태 변경, 실제 저장 성공을 구분한다.

## 3. 영역별 기대 동작

### 3.1 시작·동의·권한

근거 코드: [Consent](../../app/src/main/java/com/askthecar/Consent.kt), [MainActivity](../../app/src/main/java/com/askthecar/MainActivity.kt), [CarService](../../app/src/main/java/com/askthecar/CarService.kt), [BootReceiver](../../app/src/main/java/com/askthecar/BootReceiver.kt).

#### INIT-01 필수 동의 전 기록 제한

- 근거: 기준. 구현 상태: 구현됨, 경합·재시작 검증 필요.
- 조건: 새 설치 또는 DRIVE 동의가 꺼진 상태.
- 기대: 앱 시작·부팅 수신·서비스 시작 요청 모두 동의를 확인한다. 필수 동의 없이 주행 기록 서비스가 계속 동작하거나 사고 자료를 새로 전송하면 안 된다.
- 판정: 서비스 생존 여부, 샘플 수집, 신규 사고 파일, 네트워크 요청을 확인한다. 동의 화면이 보이는지만 확인하지 않는다.
- 예외: 철회로 발생한 원격 삭제 요청은 동의가 꺼졌다는 이유로 막으면 안 된다.

#### INIT-02 선택 AI와 권한 실패의 분리

- 근거: 기준. 구현 상태: 일부 구현, 실제 기기 동작 미검증.
- 기대: CLOUD 미동의 시 외부 AI 요청 0회. 사실 목록 생성은 가능해야 한다. 키가 없거나 AI 요청이 실패해도 기본 사고 기록을 보존한다.
- 카메라·마이크 권한 거부: 촬영·녹음 불가를 처리하고, 해당 자료가 저장됐다고 표시하지 않는다.
- 오버레이 권한 없음: 가능한 알림 경로를 사용하며 자동 화면 표시를 보장한 것처럼 보고하지 않는다.
- 센서 사용 불가: 감지 범위 축소와 실제 감지 경로를 명확히 한다. 센서 부재 시 속도 급감만으로 감지하는 현재 경로의 채택 여부는 DEC-02에서 결정한다.

### 3.2 사고 감지

근거 코드: [Crash의 ImpactSensor·CrashWatcher](../../app/src/main/java/com/askthecar/Crash.kt), [Recorder의 suddenDrop](../../shared/java/com/askthecar/Recorder.kt).

#### DET-01 보정된 충격 크기와 경계

- 근거: 기준. 구현 상태: 구현됨, 센서 처리 직접 테스트 공백.
- 현재 계산: 최초 입력으로 중력 추정치를 초기화한다. 각 이벤트에서 `gravity += (raw - gravity) × 0.02`, `d = raw - gravity`, `g = sqrt(dx² + dy² + dz²) / G` 순으로 계산한다.
- 기대: 다른 감지 조건을 배제했을 때 계산된 g가 2.5 미만이면 그 충격 경로의 콜백은 발생하지 않고, 2.5 이상이면 발생한다. 정확한 비교 연산은 `>=`다.
- 양·음 부호를 바꾼 독립된 동일 이력 시험에서 크기와 감지 여부는 같아야 한다. 방향 값은 달라질 수 있다.
- 세 축을 모두 포함한다. 한 축은 2.5g 미만이어도 합성 크기가 넘으면 현재 기준에서는 감지한다.
- 최초 샘플이 충격 상태라면 이를 중력으로 초기화할 수 있다. 이 시작 특성을 기록하고, 시작 직후 충격을 어떻게 취급할지는 DEC-02에서 결정한다.
- 금지: 원시 입력에 붙인 “2.5g” 이름이나 소수점 한 자리 결과로 보정 후 경계를 판정하는 것.
- 샘플: SAMPLE-01.

#### DET-02 속도 급감·충격·에어백의 독립 경로

- 근거: 기준 + 센서 부재 정책은 결정 필요. 구현 상태: 구현됨, 통합 검증 필요.
- 현재 급감 함수: `drop >= 15` 이면서 `drop / max(0.3, heldSec) >= 15 / 0.3`. 단위는 km/h, 초. 단순히 “0.3초에 15km/h”만으로 모든 경우를 설명하지 않는다.
- 현재 감지 루프는 약 0.3초 전 샘플을 조회한다. 속도 변화가 늦게 전달된 경우를 고려하는 `heldSec`도 검증한다.
- 센서 사용 가능 시: 급감 조건과 최근 1초 보정 충격 최고값 1.5g 이상이 함께 필요하다. 가속도 단독·에어백 경로가 별도로 있으므로 시험에서는 나머지 경로를 차단한다.
- 센서 사용 불가 시: 현재는 급감만으로 감지할 수 있다. “급감만으로는 절대 감지하지 않는다”라는 기대값을 쓰지 않는다.
- 에어백: 상승 전이이고 앱 시작 후 3초가 지나야 한다. 저장 대기 중인 사고가 있으면 앱을 켠 뒤 지난 시간과 관계없이 그 사고를 큰 사고(에어백)로 올린다. 대기 중인 사고가 없을 때만, 켠 지 60초 안에 최근 60초 안 사고가 있으면 같은 사고로 보고 새 사고를 만들지 않는다(앱 재시작 뒤 늦게 온 에어백 값). 이미 켜진 값과 새로 켜진 값을 구분해 시험한다. 시험: DRV-12(켠 직후 충격 → 0.5초 뒤 에어백).
- 판정: 결과 사고의 발생 여부·이유·심각도. 함수 테스트 통과가 센서 연결의 통과는 아니다.

#### DET-03 방지턱·요철과 의심 등급

- 근거: 향후 기획, 구체적 수치는 결정 필요. 구현 상태: 별도 의심 등급 미구현.
- 현재: 수직 충격도 DET-01에 포함하며, 2.5g 이상은 일반 사고 감지 경로로 들어간다.
- 기획 방향: 확실한 신호가 없는 의심 충격에서는 기록을 보존하되 안내·음성·휴대폰 알림을 구분하고, 사용자의 확인 또는 후속 신호로 상태를 전환한다.
- 향후 판정 항목: 기록 보존, 과도한 알림 여부, 정차·사용자 확인 후 전환, 미응답 처리, 폐기 없이 다시 확인 가능한지.
- 방지턱에 의해 감지돼도 DET-01 구현 오류와 제품 오탐 문제를 별도로 기록한다.
- 2.5~5g, 20초, 조용한 카드 60초 등 기획 수치는 실측으로 확정된 값이 아니다. 4.4에서 경계와 상태 전환을 갖춘 실험용 정책을 제안하며, DEC-01 채택과 감지 성능 검증은 별도로 진행한다.

#### DET-04 중복 신호·추가 충돌·무효 입력

- 근거: 중복 제어는 기준, 추가 충돌 모델과 입력 방어는 보강 제안/향후 기획.
- 현재: 사고 저장 대기 중 반복 신호를 억제하고, 에어백 신호가 오면 앱을 켠 뒤 지난 시간과 관계없이 심각도를 올린다(DRV-12). 대기 종료 후를 포함한 영구적인 중복 억제는 아니다.
- 기대: 같은 센서 펄스를 여러 개의 독립 사고로 처리하지 않도록 정책을 정한다. 실제 후속 충돌은 무조건 버리지 않으며 시각과 근거를 보존한다.
- 기획의 “10분 안 후속 충격은 같은 카드”는 DEC-03의 제안값이다. 4.5에서 첫 충격 기준 시간·진행 상태·수동 분리 조건을 구체화한다.
- 무효 입력 제안: NaN·무한대 등이 정상 기록을 오염시키지 않고, 이후 정상 입력 처리가 복구돼야 한다. 거부·격리·표시 정책은 정한다. 0으로 바꾸는 것을 항상 사실값으로 취급하지 않는다.
- 게임 브리지의 비유한값 정리는 구현되어 있지만 Android 원시 센서 경로의 보장을 대신하지 않는다.

### 3.3 기록 저장·복구·사고 구분

근거 코드: [Recorder](../../shared/java/com/askthecar/Recorder.kt), [CrashWatcher](../../app/src/main/java/com/askthecar/Crash.kt), [휴대폰 Sync](../../phone/src/main/java/com/askthecar/phone/Sync.kt).

#### REC-01 기록 구간과 부족한 데이터

- 근거: 기준. 구현 상태: 구현됨, 중단·실패 검증 필요.
- 평소에는 최근 60초를 메모리에서 관리한다. 사고가 없는데 상시 주행 원본을 디스크에 계속 저장하는 동작은 기대하지 않는다.
- 사고 t0 발생 시 사용 가능한 `[t0-30초, t0]`를 먼저 저장하고, 후속 수집이 끝나면 `[t0-30초, t0+10초]` 구간을 저장한다.
- 앱이 5초 전에 시작됐다면 이전 25초를 만들어 채우지 않는다. 실제 시작·종료 시각과 자료 부족을 구분한다.
- 10Hz는 목표 수집 주기다. OS 스케줄링에서 항상 정확히 400개 샘플이 생긴다는 판정은 금지한다. 단위 시험에서는 입력 샘플 집합과 구간 포함 여부를 정확히 비교한다.
- t0+10초 도달은 수집 종료 조건이며 디스크 쓰기·보고서 완료를 의미하지 않는다.

#### REC-02 저장 성공·부분 복구·실패

- 근거: 기준 + 복구 보장 보강 제안. 구현 상태: 사전 저장·임시 파일 교체·최근 기록 로딩 일부 구현.
- 필수 자료와 선택 자료를 구분한다. 기본 로그·사고 시각 등 필수 자료의 저장 여부와 AI·사진의 성공 여부를 분리한다.
- 필수 쓰기 실패는 저장 완료로 표시하지 않는다. 종료 후 남은 사전 기록은 부분 기록으로 읽을 수 있어야 하며 완성본으로 꾸미지 않는다.
- 성공적으로 저장된 기존 파일을 새 저장 실패 때문에 잘라내거나 지우지 않는다. 로그와 지문이 서로 다른 버전일 때 이를 정상 검증 완료로 취급하지 않는다.
- 판정: 파일 내용·파싱 결과·버전 일치·화면 상태. 현재 `writeAtomic`의 rename만으로 전원 차단 내구성이 검증됐다고 주장하지 않는다.
- 저장·보고서 스레드별 오류가 화면에 모두 반영되는지는 미검증이다. 복구 버튼·재시도 정책은 DEC-07에 기록한다.

#### REC-03 사고 간 격리

- 근거: 기준. 구현 상태: 현재 사고 확인 및 사진 시각 구분 일부 구현.
- 사고 A의 늦은 보고서·센서 추정·서버 응답이 사고 B의 내용이나 완료 상태를 바꾸지 않아야 한다.
- 사용자가 고른 사고 종류는 늦게 도착한 자동 추정이 덮어쓰지 않는다.
- 사진은 해당 사고의 촬영 구간에서 선택한다. 다음 사고 시작 시각은 이전 사고의 사진 구간에서 제외한다.
- 같은 초에 발생한 사고, 기기 시계 변경에 따른 ID·폴더 충돌은 추가 시험 대상이다. 현재 폴더는 초 단위 이름이므로 안전하다고 단정하지 않는다.
- 원격 지연 응답은 사고뿐 아니라 계정도 확인해야 한다. 로그아웃 뒤 다른 계정으로 로그인한 경우까지 시험한다.

#### REC-04 사고 아님과 되돌리기

- 근거: 기준. 구현 상태: 구현됨, 기록 중 경합 검증 필요.
- “사고 아님”은 즉시 영구 삭제와 다르다. 이미 저장된 자료를 표시와 함께 유지하고 정책 기간 내 되돌릴 수 있어야 한다.
- 되돌리기는 동일 자료를 다시 열며 새 사고 자료를 덮어쓰지 않아야 한다. 진행 중 사고가 있는 경우의 제한을 유지한다.
- 사고 아님 표시 뒤 선택적 외부 AI 처리를 새로 시작하지 않는 현재 방침을 검증한다. 이미 발송된 요청을 되돌릴 수 있다고 주장하지 않는다.
- 보관 만료 기준은 PRIV-02 및 DEC-04를 따른다.

### 3.4 안내·화면·응답

근거 코드: [Guide](../../app/src/main/java/com/askthecar/Guide.kt), [CrashActivity](../../app/src/main/java/com/askthecar/CrashActivity.kt), [PhoneActivity](../../phone/src/main/java/com/askthecar/phone/PhoneActivity.kt).

#### GUIDE-01 주행과 정차, 안내의 분기

- 근거: 기준. 구현 상태: 구현됨, 실제 차량 권한·축 미검증.
- 진행 중 사고의 주행 화면과 정차 후 질문을 구분한다. 설정·기록 조회의 주행 제한은 별도 화면 경로도 포함해 확인한다.
- 현재 화면 정차 판단: 속도 <1km/h 또는 P가 1.5초 이상 유지되면 정차. 속도 ≥5km/h면 주행으로 복귀하며 중간 구간에서는 기존 상태를 유지한다.
- 휴대폰에 보내는 `halted`는 별도 로직이고 같은 1.5초 판정이 아니다. 두 경로를 같은 조건이라고 가정하지 않는다. 정차 정책 통일 여부는 DEC-02.
- 부상 응답은 대상 선택을 생략하고 부상 안내로 연결한다. 에어백 사고에는 첫 질문의 “사고 아님” 선택을 표시하지 않는 현재 규칙을 검증한다.
- 사람·시설물·차량·모름, 고속도로 여부, 도로 정보 불명, 렌터카 연락처 유무를 조합한다. `Guides.steps()`의 전체 문자열 복사보다 중요한 단계의 존재·부재·선후관계를 검증한다.
- 도로를 모를 때 추정을 확정된 도로 사실로 말하지 않는다. 제한속도로 고속도로를 분류하는 현재 휴리스틱도 실제 도로 종류의 보증은 아니다.

#### GUIDE-02 응답 수정·자동 진행·음성 실패

- 근거: 기준 + 복구 UX 보강 제안. 구현 상태: 일부 구현.
- 뒤로 가서 부상·대상을 변경하면 바뀐 조건에 맞춰 안내를 갱신하며 범위를 벗어난 단계 번호로 접근하지 않는다.
- 차량 신호를 읽을 수 없는 것을 “비상등 꺼짐” 등 확정 상태로 오해하지 않는다. 자동 확인과 사용자 수동 확인을 구분한다.
- 통화 취소·통화 후 복귀·통화 상태 권한 없음의 경로를 분리한다. 통화 결과를 모르면 완료됐다고 단정하지 않는다.
- 음성 출력을 요청한 것과 실제로 들린 것은 다르다. 음성 실패 시 사용 가능한 시각 안내가 남아야 한다는 보강 요구를 검토한다. 현재 VOICE 모드는 일부 본문을 숨긴다.
- 전화 시험은 가짜 전화 처리기를 사용한다. 실제 긴급번호에 발신하지 않는다.

#### GUIDE-03 미수신 상태의 안내 중단 방지

- 근거: 제품의 정직한 표시 원칙 + 향후 차 단독 모드 기획. 구현 상태: 일부 구현.
- 서버 접수만으로 “안내는 휴대폰에 있다”고 단정하지 않는다. 현재 사고의 필요한 안내 자료 수신과 완성 기록 수신은 구분한다.
- 서버 주소 없음·휴대폰 미로그인·수신 실패에서 가능한 차 단독 안내 또는 명시적인 실패 대안을 제공한다. 상세 화면을 보려고 위험한 장소로 돌아오게 하는 흐름을 요구하지 않는다.
- 현재 `stayOut()`·`HandoffView()`는 일부 문구를 `CarSync.ok`로 고른다. `ok`는 휴대폰 저장 확인이 아니다. 차 단독 흐름과 문구 정합성을 함께 검증해야 한다.
- 정확한 안전 안내 문구·전환 방식은 기존 수칙 검토와 제품 검토를 거쳐 확정한다.

### 3.5 동기화·알림

근거 코드: [Handoff와 CarSync](../../app/src/main/java/com/askthecar/Handoff.kt), [HandoffData와 SyncClient](../../shared/java/com/askthecar/HandoffData.kt), [휴대폰 Sync](../../phone/src/main/java/com/askthecar/phone/Sync.kt), [서버](../../game/bridge/sync_server.py), [상태 표시](../../app/src/main/java/com/askthecar/CarHome.kt).

#### SYNC-01 단계별 완료의 근거

- 근거: 기준, 자료 버전 구분은 보강 제안. 구현 상태: 사고별 확인 일부 구현.
- 저장 중 / 차 저장 완료 / 서버 접수 / 휴대폰 저장 완료를 구분한다. 실패가 있으면 완료보다 실패를 우선 설명한다.
- 서버 성공 응답은 해당 사고·자료 전송에만 적용한다. 다른 사고의 확인을 재사용하지 않는다.
- 휴대폰 도착 표시는 대상 자료 저장 성공 뒤의 확인이 있어야 한다. 사고 직후 임시 자료의 확인만으로 후속 완성본까지 저장됐다고 표시하지 않는다.
- 현재 `seen`은 사고 시각만 저장한다. `ackSeen()`과 `recordAcked` 조합이 자료 버전을 구분하는지 보강 검증이 필요하다.
- 휴대폰 저장 실패 시 저장 확인을 발송하지 않아야 한다. 화면 상태가 잠시 갱신된 것만으로 저장 성공으로 판단하지 않는다.
- 샘플: SAMPLE-02.

#### SYNC-02 실패·복구·재전송

- 근거: 보강 제안. 구현 상태: 삭제·종료 재시도 구현, 일반 업로드의 영속 재전송 대기는 미구현.
- 로컬 사고 저장 성공 이후 업로드 실패가 나도 자료를 유지한다.
- 채택할 목표: 연결 복구와 재시도 시점 도래 시 추가 버튼 조작 없이 미전송 자료를 재전송한다. 앱 재시작 후에도 재전송 대상을 복구한다.
- 동일 자료 재전송은 사고 카드·알림의 불필요한 중복을 만들지 않는다.
- 삭제·철회된 사고는 재전송 대상에서 제외한다. 오래된 응답이 새 사고·새 계정 상태를 덮어쓰면 안 된다.
- 재시도 간격·횟수·수동 복구는 4.6의 제안과 DEC-05를 따른다. 다중 사고 서버 저장은 별도 구현이 필요하며, 시간 목표 없이 무한히 기다린 뒤 통과시키지 않는다.
- 샘플: SAMPLE-03.

#### SYNC-03 단계 변경·서버 재시작·자료 호환성

- 근거: 기준. 구현 상태: 일부 구현, 다중 사고 서버 복구는 제한 있음.
- 휴대폰이 보낸 단계의 반사 응답은 이미 이동한 화면을 뒤로 되돌리지 않는다. 차에서 실제로 새로 바꾼 단계와 구분한다.
- 새 사고는 새 단계 상태로 전환한다. 비어 있는 단계 목록이나 범위 밖 번호에서 앱이 종료되지 않는다.
- 서버가 재시작해 빈 상태가 왔다는 이유만으로 휴대폰에 저장된 기록을 지우지 않는다. 명시적 삭제 신호는 적용한다.
- 옛 자료 형식에 없는 제어값은 미기록으로 남긴다. “브레이크 안 밟음”, “조향 0도”를 새 사실로 만들어내지 않는다.
- 현재 서버는 계정별 최신 사고 1건을 메모리에 보관한다. 휴대폰이 꺼진 동안 여러 사고가 생겼다면 전부 복구된다고 보장할 수 없다. 다중 사고 이력 복구는 별도 향후 요구다.

#### SYNC-04 알림

- 근거: 기준, 향후 의심 등급·정차 정책은 결정 필요. 구현 상태: 일부 구현.
- 현재 휴대폰은 일반 사고에서 정차 신호, 심각한 사고에서 즉시 알림을 허용한다. 문서에 정차 후만 알림이라는 내용도 있어 DEC-02에서 통일한다.
- 알림 권한 거부나 채널 차단으로 알리지 못했으면 실제 알림 완료로 기록하지 않는다.
- 같은 사고의 재수신만으로 반복 알림을 만들지 않는다. 가족 최초 수신, 사고 다시 열기, 추가 충격의 알림은 별도 정책이다.
- 과거·미래 시각 자료와 시계 오차는 명시적으로 처리한다. 현재 `Logic.fresh()`의 음수 경과시간도 최근으로 분류하는 동작은 정책 검토 대상이다.

#### FACT-01 사실·추정·사용자 입력 구분

- 근거: 기준. 구현 상태: 일부 구현, 결과물 검증 필요.
- 시간·속도·제어값은 저장된 기록에 근거해야 한다. 없는 샘플은 기록 없음으로 처리하고, 샘플 범위 밖 질문에 근거 없는 값을 답하지 않는다.
- 운전자 선택과 센서·영상 추정을 구분한다. 재현은 추정이며 상대 차량의 실제 경로나 과실 판정이라고 설명하지 않는다.
- 두 차의 기록은 각 시계에 근거한다. 시간차·위치 오차를 숨기지 않고, 근거 없이 같은 순간으로 보정하지 않는다.
- SHA-256 지문을 표시하는 것, 파일을 재계산해 일치 확인하는 것, 위조 방지는 서로 다르다. 어떤 검증을 수행했는지 정확히 설명한다.

#### FACT-02 AI 실패와 의미 보존

- 근거: 기준 + 의미 검증 보강 제안. 구현 상태: 숫자·금지어 검사 구현, 의미 전체 검증 미구현.
- AI 미동의·키 없음·실패·검증 탈락 시 사실 목록을 사용한다. AI 실패 때문에 기본 기록이 사라지거나 열리지 않으면 안 된다.
- 원문에 없는 숫자뿐 아니라 같은 숫자를 잘못된 사건에 연결하는 것, 시간 순서를 뒤집는 것, 근거 없는 원인을 만드는 것도 제품의 사실 원칙에 어긋난다.
- 현재 `Validator`는 숫자 집합과 금지 단어를 검사한다. 그 통과를 의미의 정확성 보장으로 간주하지 않는다.
- 시험은 외부 모델을 호출하지 않고 정해진 응답으로 시작한다. 의미 보존을 자동으로 검증할 범위는 DEC-09에서 정한다.

#### SHARE-01 공유 선택과 실제 결과물

- 근거: 기준. 구현 상태: 선택 데이터 가공·PDF 생성 구현, 실제 결과물 검증 필요.
- 상대별 기본 선택과 사용자의 최종 선택을 구분한다. 제외한 위치·연락처·증권번호·진술·사진은 해당 공유 결과에서 제외되어야 한다.
- PDF 본문만 아니라 공유 본문·첨부 목록·미리보기도 확인한다. 입력에 자유문장으로 포함된 정보까지 자동 삭제하는 범위는 DEC-08에서 정한다.
- 빠르게 선택을 바꿔도 늦게 끝난 옛 생성 작업이 최신 선택의 문서를 대신 공유하지 않는다.
- 다른 사고 사진이 포함되지 않으며, 문서 생성 실패를 공유 완료로 표시하지 않는다.
- 공유 창 취소·복귀는 보험사 수신 증거가 아니다. 사용자가 완료를 표시할 때도 “보냈다고 표시함” 수준으로 기록한다.

#### SHARE-02 가족·상대 차량의 접근 범위

- 근거: 기존 양측 동의는 기준, 가족 수락·항목별 권한은 향후 기획.
- 두 차 연결은 양쪽 동의 전 상대 원문을 제공하지 않고, 철회·새 사고 때 기존 공유 범위를 정리한다.
- 가족 맡기기의 서버 성공과 가족의 실제 수락·수신 확인을 구분한다. 현재 시연의 공통 `family` 계정을 실제 가족 인증으로 설명하지 않는다.
- 향후 가족 동의 항목, 수락, 돌려받기, 가족 행동 기록의 작성자 구분은 미구현 범위를 포함해 검증한다.
- 인증된 계정·기기 연결과 권한 검사는 운영 배포 범위에서 필요하다. 시제품 서버 통과를 접근 제어 검증으로 대체하지 않는다.

#### PRIV-01 삭제 후 작업 무효화

- 근거: 기준 + 경합 보강 제안. 구현 상태: 차의 사고 폴더 쓰기(종류·충돌 전 저장·최종 저장·경위서·사진·영상 끝 시각)는 모두 `Records.write`를 거치며, 삭제(`Consent.deleteRecords`)와 같은 잠금 안에서 동의와 지금 사고 폴더를 다시 확인한다. 지운 폴더는 다시 만들지 않는다(TC-04 통과). 원격 삭제 재시도 구현. 업로드·서버 응답 순서는 미검증.
- 로컬 삭제 처리 완료 뒤 사고 목록·캐시·관련 파일이 남지 않아야 한다. 삭제 실패가 발생하면 완료로 단정하지 않는다.
- 삭제 전에 시작된 저장·보고서·종류 기록·네트워크 응답이 나중에 끝나도 삭제한 사고를 다시 생성하거나 화면에 복원하지 않는다.
- 네트워크 단절 중 원격 삭제는 대기 상태다. 연결 복구 후 처리하되 서버·휴대폰 전체 삭제가 이미 끝났다고 말하지 않는다.
- 원격 삭제 성공 뒤 늦은 업로드가 사고를 다시 활성화하지 않아야 한다. 현재 서버는 `incident` 업로드 때 `wiped`를 해제하므로 실제 요청 순서의 검증이 필요하다.
- 새로 동의하고 만든 새 사고는 이전 삭제 작업과 구분한다. 이미 외부 서비스에 발송한 요청이나 사용자 공유 앱에 전달한 사본을 회수했다고 주장하지 않는다.
- 샘플: SAMPLE-04.

#### PRIV-02 보관 정책

- 근거: 현재 정책 기준 + 향후 정책 충돌로 결정 필요. 구현 상태: 차 기간 계산·서비스 시작 시 정리 구현, 휴대폰 날짜 정리 미구현.
- 현재 차 코드: 일반 기록은 30일, 사고 아님·연습은 7일. `expired()`는 경과시간이 기간보다 **클 때** 만료한다. 정확히 같은 시각은 아직 만료가 아니다.
- 현재 정리 호출 시점: 차 서비스 시작. 기간이 지나는 순간 자동 타이머로 삭제하는 구조라고 설명하지 않는다.
- 현재 휴대폰: 로그아웃·삭제 신호에 따른 정리. 날짜 기준 정리는 없다.
- 향후 기획: 무활동·종결·연장·상한을 포함한 다른 규칙. DEC-04 확정 전 두 정책을 섞은 단일 테스트를 만들지 않는다.
- 승인 후에는 차·폰·서버·PDF 캐시 각각의 기간, 실행 시점, 연장 조건, 실패 처리와 안내 문구를 함께 검증한다.

### 4.3 합격 기준 제안을 사용하는 방법

이하의 설정 이름은 **`QA-PROPOSAL-01`**이다. 구현에 존재하는 클래스나 환경변수 이름이 아니라 결과를 구분하는 문서용 이름이다. 대상은 **다음 QA 개선 버전**이며 현재 MVP에 이미 구현됐다는 뜻은 아니다.

- 명세 담당자가 먼저 구체적인 기본안을 제공한다. 테스트 담당자는 입력과 기대값을 설정으로 주입해 시험을 구축한다. 모든 결정을 기다리며 테스트 작업을 멈출 필요는 없다.
- 아래의 숫자는 **초기 제품·시험 설계 제안**이다. 기존 코드값, 기획에서 가져온 추정값, 이번에 제안한 값을 구분한다. 이번 작업에서 성능 측정이나 실차 감지 검증은 하지 않았다.
- 결정 전에도 제안과 현재 구현의 차이를 시험할 수 있다. 결과는 `제안 기준 충족/불충족`으로 기록하고 기존 버전의 회귀 실패와 분리한다. 채택한 항목만 해당 버전의 필수 통과 기준에 넣는다.
- 결정 기록 양식: `DEC ID / 채택·수정·보류 / 최종 값 / 근거 / 담당 역할 / 대상 버전 / 날짜 / 연결 테스트`. 채택 뒤 값을 바꾸면 설정 버전을 올린다.
- 가짜 시간 시험은 지정 시각 직전·정확히 같은 시각·직후를 검사한다. 실제 기기에서 OS가 작업을 실행하지 못하는 조건은 별도로 표시하며, 실행되지 않은 작업을 시간 목표 통과로 보고하지 않는다.

### 4.4 사고와 방지턱: 감지 신호와 사용자 확인을 구분하는 제안

**연결: DEC-01·02, DET-01~03.** 센서값만으로 방지턱과 실제 사고를 완벽하게 구분할 근거는 현재 없다. 여기서는 **신호에 따른 처리 등급**을 정한다. 등급이 높다는 이유로 실제 사고·부상·과실이 입증됐다고 표시하지 않는다.

입력 정의: `g`는 DET-01의 보정 후 3축 크기, `D`는 DET-02의 급감 함수 결과, `P`는 해당 시점까지 최근 1초의 최고 g다. 에어백은 유효한 새 전개 신호다. 시작 시 이미 켜진 값과 통신 재전송은 별도이며, 현재 초기 억제 구간의 회귀 시험은 유지한다.

| 우선순위 | 입력 조건 | 제안 처리 | 근거 |
|---|---|---|---|
| 1 | 사용자 “사고예요” 또는 직접 기록 | 사용자 확인 사고로 기록·안내. 센서가 사고를 증명했다고 표시하지 않음 | 제품 흐름 |
| 2 | 유효한 새 에어백 전개 | 우선 안내 대상으로 승격 | 기존 경로 |
| 3 | 가속도 사용 가능하고 `D=true` 및 `P >= 1.5g` | 우선 안내 대상으로 승격 | 기존 복합 경로 |
| 4 | `g >= 5.0` | 우선 안내 대상으로 승격 | 기획의 추정 경계, 실측 필요 |
| 5 | `2.5 <= g < 5.0`, 위 조건 없음 | 의심 충격으로 저장하고 확인 대기 | 2.5는 기존 경계, 등급은 기획 제안 |
| 6 | 가속도 사용 불가이고 `D=true`, 에어백·사용자 확인 없음 | 의심 충격 + 센서 제한 표시 | 이번 보강 제안. 현행 급감 단독 감지와 다름 |
| 7 | 위 조건 없음 | 이 정책에 의한 새 자동 사고 없음. 수동 기록은 계속 가능 | 감지 한계 명시 |

의심 충격의 상태 전환 제안:

1. 감지 시각을 `ts`로 저장하고 사용 가능한 전 30초·후 10초 자료를 보존한다. **수직 충격이라는 이유만으로 삭제하거나 방지턱으로 확정하지 않는다.**
2. 주행 중에는 비차단 표시만 하고 음성·폰 사고 알림을 내지 않는다. `ts+20초`에 정차 여부를 재평가하되 미정차라고 사고 아님으로 자동 확정하지 않는다. 대기는 계속된다.
3. 정차 판단은 이 제안에서 GUIDE-01의 `<1km/h 또는 P, 1.5초 유지`를 사용한다. 정차가 확인되면 조용한 확인 카드를 한 번 보여 준다. 표시 시각부터 60초 후 무응답이면 접는다. 주행으로 돌아가면 질문을 숨기되 타이머를 새로 늘리지 않는다.
4. “사고예요”는 사용자 확인 사고로 승격한다. “아니에요”는 사고 아님으로 표시한다. 무응답은 `미확인 충격`이며 사용자 부정 응답과 구분한다. 접은 뒤에도 기록에서 다시 확인할 수 있다.
5. 기다리는 중 에어백·복합 급감·5g 이상 신호가 들어오면 즉시 우선 등급으로 올린다. 같은 기록을 중복 생성하지 않는다. 주행 중에는 비차단 안내, 정차 후에는 질문을 제공한다.
6. 폰 알림은 의심 상태에서는 0회. 사용자 확인 또는 우선 등급은 정차 확인 후 사고당 최초 1회, 유효한 에어백 전개는 정차를 기다리지 않는 예외를 제안한다. 같은 신호 재수신은 추가 알림을 만들지 않는다. 추가 충격은 일지에 남기되 이 초안에서는 별도 폰 알림을 늘리지 않는다.
7. 유한하지 않은 값은 그 센서 이벤트만 격리하고 오류를 남긴다. 중력 추정 상태를 오염시키지 않으며 다른 유효한 에어백 경로는 막지 않는다. 이후 정상값 처리 복구를 확인한다.

**합격 예:** 보정값 3g만 있는 수직 펄스 → 기록 1건·의심 상태·음성/폰 알림 0회. 같은 3g에서 유효한 급감까지 있음 → 우선 등급. 보정값 4.999g와 5.000g는 다른 등급. 에어백 신호는 g가 작아도 우선한다. 정차 후 카드 59.999초에는 열림, 60초에는 접힘, 자료는 유지된다.

이 시험은 **규칙 구현의 정확성**을 확인한다. **사고 구분 능력**을 평가하려면 정답을 별도로 붙인 방지턱·급제동·정면·측면·저속 접촉 입력을 모아 오탐·미탐을 각각 집계해야 한다. 기획의 5g와 이번 20/60초 정책을 실차의 검증된 합격선으로 사용하지 않는다. 새 신호 조합을 release에 적용하기 전 기존 2.5g 정책과 동일 입력으로 비교하고, 놓치게 된 사례를 검토한다.

### 4.5 반복 신호와 추가 충돌을 구분하는 제안

**연결: DEC-03, DET-04, REC-01·03.** 기획의 10분을 기본안으로 사용하되 기준 시각과 예외를 고정한다.

- **한 펄스의 중복 제어:** 최초 충격부터 g가 1.0 미만으로 연속 500ms 유지되기 전까지 같은 충격 구간으로 묶는다. 정확히 1.0g는 해제 조건이 아니다. 유효한 센서 입력이 없거나 입력 간격이 250ms를 초과하면 그 구간을 연속 저충격 시간으로 계산하지 않는다. 1.0g·500ms·250ms는 이번 시험용 제안값이다.
- 구간 안에서는 충격 시작 시각·최고값·모든 원시 샘플을 보존하고 새 카드를 만들지 않는다. 더 높은 등급 신호·새 에어백 전개는 억제하지 않고 즉시 반영한다. 이 묶음이 물리적으로 충돌 한 번이었다는 뜻은 아니다.
- 가속도 없는 경로는 D가 참인 연속 구간을 하나로 묶고, 유효한 속도 관측에서 D가 거짓으로 연속 500ms 유지돼야 재활성화한다. 샘플 간격 250ms 초과는 동일하게 연속성 단절로 처리한다. 수동 기록은 센서 재활성화를 기다리지 않는다.
- **후속 사건의 카드 연결:** 같은 계정·같은 차량이고 기존 카드가 진행 중이며 `0 <= 새 충격 시각 - 첫 충격 시각 <= 600초`이면 같은 카드에 별도의 추가 충격 사건을 붙인다. 기준은 마지막 충격이 아니라 첫 충격이다. 각 사건의 시각·최고값·등급을 보존한다.
- 600초 초과, 이전 카드 종결/사고 아님, 계정·차량 변경 또는 사용자 “별개 사고” 선택이면 새 카드로 만든다. 의심 충격의 단순 접힘은 종결과 다르다. 사용자가 나중에 분리해도 원래 관찰 시각·자료를 잃지 않는다.
- 각 추가 사건은 사용 가능한 전 30초·후 10초를 보존한다. 겹친 샘플은 공유할 수 있지만 처음 사건의 기록을 덮어쓰지 않는다. 첫 사건의 후속 10초 종료 때문에 다음 충돌 수집을 버리지 않는다. 새 자료가 생기면 완성본 버전을 올린다.
- 기기 시계가 바뀌거나 재시작으로 경과시간 연속성이 불명확하면 시간만으로 자동 합치지 않고 별도 카드에 `관련 여부 미확인`으로 남긴다.

**합격 예:** 한 펄스의 연속 20개 샘플 → 사건 1개. 재활성화 후 t0+8초 충격 → 카드 1개·사건 2개·두 사건 자료 보존. t0+600초 → 같은 카드. t0+600.001초 → 새 카드. t0+100초라도 이미 종결했으면 새 카드. 해제 전 두 물리 충돌이 섞인 입력도 원시 자료를 버리면 실패다.

### 4.6 업로드 재시도의 구체적인 제안

**연결: DEC-05·06, SYNC-01·02, SAMPLE-02·03.** 일반 사고 업로드를 대상으로 한다. 삭제 요청은 이 절의 24시간 중단 규칙을 적용하지 않는다.

| 항목 | 제안 기준 |
|---|---|
| 최초 전송 | 필수 로컬 저장 완료 후 온라인·인증 유효·실행 가능 상태면 2초 이내 시작 |
| 실패 후 간격 | 앞 요청의 **실패 확정 시각부터** 5초 → 15초 → 30초 → 60초 → 300초 대기. 최초 포함 최대 6회가 첫 묶음 |
| 계속 실패 | 6번째 실패 뒤 15분 간격으로 1회씩. 최초 큐 등록부터 24시간 미만까지만 자동 시도 |
| 24시간 경계 | 정확히 24시간부터 새 자동 요청 0회. 로컬 기록 유지·수동 재전송 필요 표시. 시작된 요청은 아래 제한시간까지만 처리 |
| 요청 제한시간 | 업로드 1회의 연결·본문 전송·응답 수신 합계 최대 10초. 초과 시 실패 확정. long-poll에는 적용하지 않음 |
| 일시 오류 | 연결 오류·제한시간 초과·HTTP 408·5xx는 재시도 |
| 인증/요청 오류 | 401·403은 재인증 전 중단. 기타 4xx는 자동 반복 중단·원인 표시. 429는 아래 별도 처리 |
| 429 | 유효한 Retry-After가 있으면 정책상 다음 시점과 서버 지정 시점 중 더 늦은 때 실행. 없거나 해석 불가면 기본 간격. 24시간 한계는 유지 |
| 성공 | 올바른 사고·버전의 성공 응답 뒤 해당 업로드 큐 제거. 폰 저장 완료 표시는 별도의 버전별 확인이 있어야 함 |

동작 조건과 예외:

1. **알려진 오프라인 동안 요청 0회.** 호출하지 않은 요청은 실패 횟수를 늘리지 않는다. 첫 묶음 안에서 연결 복구를 감지하면 기본 대기를 한 번 앞당겨 2초 이내 1회 재시도할 수 있다. Retry-After와 6회 소진 뒤의 15분 대기는 앞당기지 않는다. 복구 알림 중복으로 횟수·대기를 초기화하지 않는다.
2. 모든 시작 조건은 `현재 시각 < 등록+24시간`, 원본 보관기간 유효, 동의 유효, 계정 일치다. 재시작 때 등록 시각·실패 횟수·다음 시각을 복구하며 누적 대기 작업을 한꺼번에 몰아 실행하지 않는다.
3. 같은 계정·사고는 동시 요청 최대 1개다. 재시도는 같은 자료 버전을 식별할 수 있어야 한다. 새 완성본이 생겼다면 최신 버전을 대기시키고 옛 응답으로 최신 버전의 성공/수신 상태를 바꾸지 않는다. 새 버전 때문에 최초 등록 시각이나 실패 횟수를 초기화하지 않는다.
4. 삭제·철회·로그아웃 시 기존 계정의 전송을 중단한다. 삭제/철회된 자료는 대기열에서도 제거한다. 다른 계정 로그인으로 옛 전송이 재개되면 실패다. 원격 삭제와 늦은 요청의 무효화는 SAMPLE-04로 검증한다.
5. 인증 복구 또는 24시간 경과 뒤 수동 재전송은 유효한 자료에 한해 새 24시간 묶음을 시작할 수 있다. 보관 기한은 연장하지 않는다. 중복 버튼은 하나의 작업으로 합친다. 서버 성공 뒤 폰 미수신은 업로드 실패와 별도 상태다.
6. 실제 앱이 OS에 의해 정지된 동안 2초 실행을 보장하지 않는다. 다음 실행 가능 시점에 이미 기한이 지난 작업 하나를 2초 이내 시작하되 24시간 만료·Retry-After·삭제 여부를 먼저 확인한다. 기한 내 백그라운드 실행 자체의 지원 여부는 별도 기기 시험 결과로 보고한다.
7. 가짜 스케줄러 시험은 정확한 예정 시각을 검사한다. 실행 중인 기기 통합 시험은 예정 시각 전 요청 금지, 예정 시각 후 2초 이내 시작을 목표로 한다. OS 중단은 통과가 아니라 환경 제약으로 분리한다.

**정확한 시험 예:** 첫 실패 확정 시각을 f0=0으로 하고 각 실패 응답을 즉시 반환하면 재시도 시작은 5, 20, 50, 110, 410초다. 410초의 여섯 번째 실패 뒤 다음은 1310초다. 실제 응답이 늦으면 그 실패 확정 시각부터 다시 간격을 센다. f0+4.999초 요청 0회, +5초 요청 1회. 24시간까지 모두 실패하고 계속 온라인이며 응답이 즉시 실패하는 고정 시험은 최초 포함 총 101회이며, 24시간 경계부터 추가 자동 요청은 0회다. 이 횟수는 응답 지연·오프라인·429가 없는 해당 시험에만 적용한다.

근거: 기존 코드는 일반 업로드 영속 재시도를 제공하지 않는다. 5/15/30/60/300초·15분·24시간·10초는 이번 운영 부하와 복구 지연을 조절하기 위한 초안이다. 사용자 규모·통신량을 측정한 최적값은 아니다. 서버가 최신 사고 하나만 유지하는 구조로는 여러 미전송 사고의 온전한 복구를 보장할 수 없으므로, 다중 사고 저장을 함께 구현하거나 해당 기능을 미지원으로 남겨야 한다.

### 4.7 차·폰·서버의 보관과 삭제 제안

**연결: DEC-04·07, PRIV-01·02, SAMPLE-04.** 이번 QA 개선 버전에는 기존 동의문의 30일/7일을 바탕으로 한 짧은 정책을 제안한다. 기획에서 채택한 장기 보관 방향(90일 무활동·종결 후 30일·상한 1년)을 취소하는 결정은 아니며, 적용 버전·동의 문구를 팀이 정해야 한다. 장기 정책을 채택하면 아래 제안을 수정한 뒤 시험한다.

공통 제안: 1일은 24시간, 기간 시작은 사고 최초 시각 t0다. 수정·열람·동기화·추가 충격·수동 재전송은 t0를 갱신하지 않는다. 일반 사건은 t0+30일, 사고 아님·연습·접힌 미확인 충격은 t0+7일에 만료한다. **`현재 >= 만료 시각`이면 만료**로 제안하며, 현재 코드의 `>`와 다른 정책 변경임을 명시한다. 만료 전 사용자 확인으로 일반 사건이 되면 t0+30일로 바꾸지만 이미 삭제된 자료를 복원하지 않는다.

| 저장 위치 | 제안 보관 규칙 | 정리·접근 차단 시점 |
|---|---|---|
| 차 로컬 | 해당 사건의 30일/7일. 사진·진술·보고서 포함 | 서비스 시작·사건 열기/공유/업로드 전에 만료 검사. 실행 중 정리 검사는 1시간마다 |
| 폰 로컬 | 차와 같은 t0·만료 시각. 내려받은 날짜로 연장 금지 | 앱/동기화 시작·열기/공유 전 검사. 실행 중 정리는 1시간마다 |
| 서버의 전달용 본문 | `사건 만료`, `해당 버전 최초 접수+24시간`, `대상 폰의 해당 버전 저장 확인+1시간` 중 가장 이른 시각까지 | 모든 읽기/쓰기에서 만료 검사, 실행 중 1시간마다 정리. 중복 업로드로 버전 접수 시각 갱신 금지 |
| 앱 소유 임시 PDF·미리보기·공유 캐시 | `생성+24시간`과 `사건 만료/명시적 삭제` 중 더 이른 시각까지 | 앱 시작·공유 전 검사, 실행 중 1시간마다 정리 |

- 서버 규칙은 **전달용 임시 보관**이다. 클라우드 원본 백업·24시간 넘게 꺼져 있던 폰의 자동 복구까지 보장하지 않는다. 그 기능이 필요하면 서버 보존 정책과 동의를 별도로 바꾼다. 현재 메모리 서버에는 이런 TTL(자동 보관 만료 시간) 및 버전별 만료 모델이 없다. 전달용 본문만 만료된 것은 사용자 삭제 신호가 아니므로 폰의 유효한 로컬 기록을 지우지 않는다.
- 만료 자료는 목록·열기·공유·새 업로드에 즉시 사용 불가다. 물리 파일 정리는 실행 중 다음 정리 주기 이내 시도하며, 이미 종료된 앱의 파일이 정확한 만료 시각에 지워졌다고 보고하지 않는다. 재시작 시 접근 허용 전에 검사한다. 삭제 실패는 상태와 재시도 대상으로 남긴다.
- 사용자 삭제·동의 철회는 기간을 기다리지 않는다. 즉시 접근·생성·업로드를 막고 로컬 삭제를 시도한다. 원격 삭제는 온라인·실행 가능 상태에서 2초 이내 시작한다. 실패하면 30초 간격으로 재시도하며 성공 전까지 대기 표시를 유지한다. 24시간이 지났다고 삭제 요청을 폐기하지 않는다.
- 삭제 대기열에는 사건 본문 대신 필요한 최소 식별 정보만 둔다. 성공 확인 후 해당 대기 항목을 없앤다. 늦은 업로드 거절에 필요한 삭제 표식·계정 세대 정보는 별도의 제어 정보로 관리한다. 삭제된 사건의 표식은 원래 일반 보관 상한인 t0+30일까지 유지하고, 그 뒤에도 원래 시각이 만료된 요청은 거절한다. 철회된 계정 세대의 요청은 새 동의 세대에서도 유효해지지 않는다.
- 오프라인 폰은 서버 삭제 사실을 즉시 알 수 없다. 연결·동기화 복구 시 삭제 신호를 적용하고, 그 전에 모든 기기에서 지워졌다고 표시하지 않는다. 서버의 본문 만료와 삭제 신호 보존을 분리해 오프라인 폰이 삭제를 놓치지 않도록 한다.
- 다른 앱에 이미 전달된 PDF, 사용자가 별도로 저장한 사본은 앱 내부 삭제의 보장 범위 밖이다. 서버 재전송·동기화로 만료되거나 삭제된 자료를 되살리면 실패다.

**합격 예:** t0+30일-1ms에는 일반 사건 접근 가능, 정확히 +30일에는 접근 불가. t0+6일에 사고 아님으로 바꿔도 +7일에 만료. 앱이 +31일에 시작되면 화면에 노출하기 전에 차단. 서버 중복 전송이 TTL을 늘리면 실패. 저장/전송 작업이 삭제 후 완료돼 자료를 복원하면 실패. 디스크 삭제 실패인데 전체 삭제 완료라고 표시해도 실패.

### 4.8 성능 합격선의 초기 제안

**연결: DEC-10, OPS-02.** 아래 수치는 이번에 제안한 **초기 지연 예산**이다. 현재 앱의 측정 결과나 검증된 차량 성능 기준이 아니다. 기준 기기를 고정해 측정한 뒤 채택·수정하며, 수정 이유를 남긴다.

| 측정 대상 | 시작 → 종료 이벤트 | p95 목표 | 개별 최대값 |
|---|---|---|---|
| 충격 판단 | 앱의 센서 콜백 진입 → 감지 결정/콜백 발생 | 50ms 이하 | 200ms 이하 |
| 정차 중 사고 화면 | 정차 조건 충족 및 감지 결정 → 필요한 첫 질문 프레임 표시 | 500ms 이하 | 1초 이하 |
| 사전 로그 저장 | 사고 감지 → 사용 가능한 사고 전 로그의 성공적인 파일 교체 완료 | 500ms 이하 | 2초 이하 |
| 후속 로그 저장 | t0+10초 수집 종료 조건 충족 → 필수 로그 저장·재읽기 성공 | 1초 이하 | 3초 이하 |
| PDF 생성 | 고정 공유 입력의 생성 요청 → 파싱 가능한 PDF와 공유 URI 준비 | 2초 이하 | 5초 이하 |

측정 계약:

1. 기준 환경은 팀이 실제 사용할 에뮬레이터/기기 **한 구성**을 등록한다. 모델, OS/API, CPU/RAM, 에뮬레이터 CPU/RAM 할당, 호스트, APK 커밋·빌드 종류를 결과에 필수 기록한다. 미등록 환경의 결과는 합격 선언 없이 참고값으로 남긴다. debug와 release 수치는 섞지 않는다.
2. 센서·화면·저장 시험은 준비된 앱, 동의/필요 권한 허용, 저장공간 여유, AI·사진 처리 비활성 조건이다. 주행·권한 차단으로 질문을 표시하면 안 되는 경우는 화면 지연 시험 대상에서 제외하고 별도 기능 시험한다. 화면 시험은 이미 정차 상태로 고정해 1.5초 정차 대기를 섞지 않는다.
3. 저장 입력은 t0-30초부터 t0+10초까지 100ms 간격의 **합성 샘플 401개**로 고정한다. 이 샘플 수는 시험 데이터 정의이며 실기기 수집 보장이 아니다. 최종 로그 내용·시각·샘플 수가 정확해야 한다. 보고서·AI·사진 완료 시간은 이 로그 저장 지표에서 제외하되 UI의 전체 완료와 혼동하지 않는다.
4. PDF 입력은 고정된 사건 1건, 위 합성 로그, 1,000자 진술, 사진 5장(각 1280×720 JPEG, 1MiB 이하)으로 시작한다. 팀이 fixture 파일을 생성해 해시를 기록하고 이후 같은 파일을 쓴다. 다른 사진 압축률·데이터로 바꾼 결과는 별도 집계한다.
5. 워밍업 5회 뒤 각 항목 100회를 측정한다. p95는 100개 소요시간을 오름차순 정렬한 **95번째 값**이다. 100회 모두 내용 검증 성공, p95 목표 만족, 개별 최대값 초과 0회여야 해당 환경에서 통과다. 실패·중단된 실행을 표본에서 빼지 않는다.
6. 실제 기기 성능은 단조 증가 시계로 잰다. 가짜 시간으로 지연 없이 통과시킨 결과는 성능 증거가 아니다. 네트워크 복구 성능은 4.6의 통제된 서버 조건으로 별도 측정한다.
7. 첫 실행·저장공간 부족·대용량 사건·장시간 실행은 별도 결과로 남긴다. 메모리·전력·접근성의 합격선까지 위 지연 목표로 대신하지 않는다. 이 항목들은 DEC-10의 남은 결정이다.

**판정 예:** 100회 모두 400ms여도 센서 판단의 p95 50ms와 최대 200ms를 넘으므로 실패다. 최종 로그가 t0+10초 이후 800ms 안에 저장돼도 샘플이 빠졌으면 실패다. p95가 목표 이내라도 한 번 최대값을 넘으면 해당 조건에서는 실패다.

### SAMPLE-01 센서 보정과 임계값

**연결:** DET-01. **종류:** 결정적인 계산 시험. **상태:** 현재 구현 회귀 검증. **게임/외부 서버:** 불필요.

#### 준비

1. 각 행마다 새로운 중력 추정 상태를 만든다. 다른 행의 상태를 재사용하지 않는다.
2. G는 실제 앱 상수를 사용한다. 센서 입력 표현이 Float라면 같은 Float 변환을 거쳐 입력한다.
3. 에어백은 꺼짐, 속도는 일정. 다른 사고 감지 경로를 작동시키지 않는다.
4. 가짜 시각 t=0에 `(0, G, 0)`을 넣어 초기화한다. 초기 이벤트의 콜백은 0회여야 한다.
5. t=0.02초에 아래 입력 한 번을 넣고 그 직후 관찰한다. 실제 sleep은 하지 않는다.

| 행 | 두 번째 원시 입력 (m/s²) | 보정 후 예상 g | 이 이벤트의 콜백 |
|---|---|---|---|
| A | `(0, G, 2.54G)` | 약 2.4892 | 0회 |
| B | `(0, G, 2.56G)` | 약 2.5088 | 1회 |
| C | `(0, G, -2.56G)` | 약 2.5088 | 1회 |
| D | `(0, G + 2.56G, 0)` | 약 2.5088 | 1회 |

중력 추정치를 먼저 2% 갱신하므로 초기 수평축 0에서 한 번 변한 입력의 잔여 크기는 입력 변화량의 0.98배다. 이 표는 임계값에서 충분히 떨어져 Float 반올림으로 결과가 흔들리지 않도록 했다.

#### 판정

- 보정값 허용오차: `1e-5 g`. 콜백 횟수는 정확히 비교한다.
- B·C의 크기와 감지 여부는 같아야 한다. 방향은 반대일 수 있으며 별도 방향 테스트로 확인한다.
- D가 감지되는 것은 **현재 3축 크기 기준**의 기대다. 방지턱 오탐 해결 완료라는 뜻은 아니다.
- 순수한 임계값 비교를 분리했다면 정확한 `2.5` 입력에 대해 참, `2.5 - 1e-9`에 대해 거짓도 검증한다. Float 센서 경계 시험과 이 비교 시험을 혼동하지 않는다.
- 같은 원시 벡터를 여러 번 넣는 시험은 중력 추정치가 바뀐다. 그 결과를 이 단일 이벤트 표와 비교하지 않는다.

#### 필요한 관찰·실패 출력

원시 벡터, 갱신 전후 중력 추정치, 계산 g, 콜백 횟수·인자. 실제 `ImpactSensor`가 사용하는 계산을 호출해야 한다. 현재 Android 콜백에 계산이 묶여 있으므로 동작을 바꾸지 않는 최소 분리 또는 Android 시험 어댑터가 필요하다.

### SAMPLE-02 임시 자료 수신을 완성본 도착으로 오인하지 않기

**연결:** SYNC-01, GUIDE-03. **종류:** 저장·확인·표시 통합 시험. **상태:** 자료 버전 구분은 보강 제안, 현행 동작 차이 확인. **게임:** 불필요.

`A/preview`, `A/final`은 의미를 설명하기 위한 표기다. 현재 JSON에 이러한 필드가 있는 것은 아니다. 실제 식별 방식은 DEC-06으로 정한다.

#### 준비와 순서

1. 합성 계정 `qa-driver-a`, 사고 A의 t0=`1700000000.0`. 기존 사고·확인 상태는 비운다.
2. t0+1초: 휴대폰이 A의 임시 자료를 성공적으로 저장한다. 지문은 null, 후속 기록은 아직 없다. 저장 확인이 서버·차에 전달된다.
3. t0+10초 이후: 차에서 A의 완성본 필수 자료 저장을 성공시킨다.
4. 서버는 완성본 업로드에 200을 반환한다.
5. 휴대폰이 완성본을 받지만 해당 저장 시도는 실패하도록 설정한다. 이전 임시 자료는 유지한다.
6. 이 시점의 완료 표시와 안내 문구를 관찰한다.
7. 다음 저장 시도는 성공시킨다. 확인 응답은 잠시 지연시켜 저장만 된 상태를 관찰한다.
8. 완성본 저장 확인을 차에 전달하고 다시 관찰한다.

#### 기대 결과

- 5~6번: 차 저장 완료·서버 접수는 표시 가능. **완성본의 휴대폰 도착 완료는 표시 불가**. 임시 안내자료의 도착은 별도로 설명할 수 있다.
- 실패한 완성본 저장에 대해 성공 확인을 보내지 않는다. 임시 자료의 과거 확인을 완성본 확인으로 쓰지 않는다.
- 7번: 차가 아직 완성본 확인을 받지 않았으므로 차의 완료 표시는 앞 단계에 머문다.
- 8번: 사고 A의 올바른 완성본 확인을 받은 뒤 완료로 전환한다.
- 변형: 사고 B의 확인을 보내도 A는 완료로 바뀌지 않는다. 같은 확인이 중복돼도 카드·일지는 불필요하게 중복되지 않는다.

#### 판정과 현재 공백

`recStage()`에 이미 올바른 Boolean을 넣는 시험만으로 끝내지 않는다. 휴대폰 저장 성공/실패 → 확인 생성 → 차 상태 → 문구의 연결을 검증한다. 현재 시각 기반 `seen`과 `CarSync.ok` 문구 사용 때문에 자료 버전 계약이 필요하다. 현재 빌드에서 실패할 가능성은 있으나 실행 재현 전 확정 버그로 기록하지 않는다.

### SAMPLE-03 실패한 사고 업로드의 자동 복구

**연결:** SYNC-02, REC-03. **종류:** 가짜 네트워크·스케줄러 통합 시험. **상태:** 일반 업로드 복구 보강 제안. **게임/실제 인터넷:** 불필요.

#### 준비와 순서

1. 계정 A의 사고 A 완성본을 로컬에 성공적으로 저장한다.
2. 첫 업로드를 네트워크 오류로 실패시킨다. 성공 응답을 반환하지 않는다.
3. 사용자의 버튼 조작·종류 변경·추가 사고 이벤트를 전혀 발생시키지 않는다.
4. 네트워크를 성공 응답 가능 상태로 바꾼다.
5. `QA-PROPOSAL-01`의 4.6 정책을 주입한다. 첫 실패 확정 후 4.999초에는 재요청 0회, 정확히 5초에는 재요청 1회인지 확인한다. 이 기본 시험에서는 네트워크 요청의 성공 가능 상태만 바꾸고 연결 복구 이벤트는 발생시키지 않는다. 복구 이벤트를 보내 2초 이내 시도하는 시험은 별도 변형으로 실행한다.
6. 서버는 같은 사고 A의 업로드에 성공 응답한다. 휴대폰 확인은 아직 보내지 않는다.
7. 휴대폰 저장 성공과 해당 자료의 확인을 전달한다.

#### 기대 결과

- 2번 이후에도 로컬 A의 내용은 보존된다. 미전송 상태를 식별할 수 있다.
- 5번에서 별도 사용자 행동 없이 정해진 시각에 A가 재전송된다. 재시도 요청은 허용하지만 서버·폰의 사고 카드가 중복 생성되면 안 된다. 간격·24시간 중단·재시작 복구·오류별 처리는 4.6의 경계 시험을 추가한다.
- 6번은 서버 접수까지만 완료다. 7번에서 휴대폰 도착 상태로 전환한다.
- 변형 1: 실패 후 앱 인스턴스를 재생성해도 미전송 대상을 복구한다.
- 변형 2: 재시도 전에 삭제한 A는 보내지 않는다.
- 변형 3: 계정 B로 전환했을 때 A의 자료가 B의 경로로 전송되지 않는다.

#### 판정과 현재 공백

현재 `CarSync.publish()`는 일반 업로드의 영속 대기·재시도를 보장하지 않는다. 삭제·종료 재시도가 있다는 이유로 이 시험을 통과 처리하지 않는다. 동료는 “아무 새 이벤트 없이 재전송을 일으키는 경로”를 관찰해야 한다. 요구 채택 후 구현 전에는 미구현 실패로 분류한다.

### SAMPLE-04 삭제와 늦은 작업 완료의 경합

**연결:** PRIV-01, REC-03, SYNC-02. **종류:** 실행 순서를 제어하는 통합 시험. **상태:** 기존 삭제 약속의 검증 + 경합 방어 보강. **게임:** 불필요.

#### 준비와 순서

1. 합성 사고 A를 만들고 정상적으로 읽을 수 있는 초기 파일을 저장한다.
2. 아래 작업을 각각 독립된 변형 시험에서 대기시킨다. 실행 중인 작업은 barrier(시험이 해제하기 전 진행하지 않는 지점)로 멈춘다.
   - a. 사전 저장/보고서 작업이 디스크 쓰기 직전인 상태.
   - b. 종류 저장 작업이 사고 폴더 참조를 잡고 디스크에 처음 닿기 직전인 상태.
   - c. 삭제 전에 시작된 업로드 또는 서버 응답이 지연된 상태.
3. 사용자가 동의를 철회한다. 로컬 삭제 처리가 끝난 뒤 파일·목록·현재 사고 상태를 확인한다.
4. 서버 삭제 요청은 처음에는 실패시켜 대기 상태를 확인한다.
5. 연결 복구 후 서버 삭제를 성공시킨다. 연결된 휴대폰이 삭제를 적용하도록 한다.
6. 2번에서 대기시킨 작업을 해제하고, 예약된 재시도·콜백을 모두 진행한다.

#### 기대 결과

- 3번의 성공한 로컬 삭제 이후 A의 파일·카드·진술·관련 캐시가 복원되지 않는다. 파일 삭제 실패를 주입한 시험에서는 성공 표시를 기대하지 않는다.
- 4번에서 원격 전체 삭제 완료로 표시하지 않는다. 삭제 재시도 정보는 유지된다.
- 5번 이후 늦은 업로드가 서버 사고 A를 다시 활성화하지 않는다. 늦은 응답이 폰과 차의 A를 복원하지 않는다.
- 재시작해도 A가 다시 나타나지 않는다.
- 변형: 다시 동의해 만든 새 사고 B는 과거 A 작업과 구분되며 A의 늦은 결과가 B를 덮어쓰지 않는다.

#### 판정과 현재 공백

파일 존재뿐 아니라 폴더 재생성, 서버 상태, 화면 상태, 재시도 대상을 함께 확인한다. 차의 로컬 쓰기는 `Records.write`가 삭제와 같은 잠금 안에서 DRIVE 동의와 지금 사고 폴더(`CrashFlow.dir`)를 다시 확인하므로, 2-a·2-b 변형은 이 가드로 막힌다. 이 가드는 차의 로컬 파일만 지킨다. 서버의 `wiped`는 새 `incident` 요청으로 해제될 수 있어 실제 순서 검증이 필요하다. 이미 처리된 외부 AI 요청의 회수나 다른 공유 앱의 사본 삭제는 이 시험의 보장 범위가 아니다.

6. 테스트를 위한 최소 분리와 제품 동작 변경은 구분해 리뷰한다. 샘플 준비를 이유로 큰 구조 개편을 동시에 하지 않는다.

결과 위치 예: `app/build/reports/tests/testDebugUnitTest/index.html`, `phone/build/reports/tests/testDebugUnitTest/index.html`. 실행기의 실제 결과 경로도 확인한다. 환경 구성 실패는 제품 기능의 실패와 구분한다.

### 7.3 게임 시험의 해석 제한

- [beamng_bridge.py](../../game/bridge/beamng_bridge.py)는 조건에 따라 에어백·3.5g 펄스를 합성하고 수평 충격 지속시간을 보정한다. 게임 물리값이 앱에 그대로 도착한다고 가정하지 않는다.
- [crash_suite.py](../../game/bridge/crash_suite.py)는 정면·측면·후방·후진 및 `hard_brake` 등 기존 시나리오가 있다. 우선 재사용한다.
- `g` 요약값은 소수점 한 자리로 반올림된다. 정밀 임계값 판정은 원시 계산값으로 한다.
- 비충돌 시험은 필요할 때 끝에 `TEST_CRASH`로 기록을 만든다. 그 팝업은 실제 오탐과 구분한다. `TEST_CRASH` 자체는 2.5g 계산을 검증하지 않는다.
- 자동 `false` 판정에는 손상량 조건이 포함된다. 방지턱에서 게임 손상이 난 경우 해당 값만으로 오탐 부재를 결론 내리지 않는다.
- 스크립트 완료·기록 생성은 전체 통과가 아니다. 결과 파일의 `error`, 감지 여부, 기대 방향, 자료 누락을 확인한다.
- 브리지의 일부 self-check 내부값은 실행 기본값과 다르다. 실제 실행 옵션을 결과에 기록한다.
- 상세 환경·게임 조작은 [README_TEST](../../README_TEST.md)를 따른다. 사람 운전과 자동 입력을 동시에 실행하지 않으며 실제 긴급번호로 발신하지 않는다.

## 8. 역할·결과 기록·종료 기준

### 8.1 역할

- 명세 담당자: 요구 근거 정리, 기대값 정의, 정책 결정 대장 관리, 샘플 입력·예상 결과 제공.
- 테스트 시스템 담당자: 제어 지점·고정 데이터·실행 환경 구현, 요구사항 ID를 테스트에 연결, 실행 결과 수집.
- 공동: 미구현 요구 채택·대상 버전 결정, 실패 원인 검토, 기기·게임에서 대체 객체의 한계 확인.

### 8.2 시험 결과 양식

```text
요구사항 ID / 샘플 ID:
채택 상태 / 대상 버전:
분석·실행 커밋 / APK 빌드 종류:
기기·OS·SDK / 서버·브리지 설정:
입력 데이터·시간·작업 순서:
기대 결과:
실제 결과:
검증 상태:
근거 파일·이벤트·로그·화면:
원인 분류: 구현 오류 / 미구현 / 요구사항 미정 / 환경 / 시험 도구
후속 작업 / 담당 역할:
```

실행하지 않은 항목, 예상 실패, 환경 차단, 무시된 테스트를 통과 개수에 넣지 않는다. 알려진 미구현 실패는 추적 이슈·담당·대상 버전을 붙여 별도 집계한다. 이미 통과하던 요구의 실패는 회귀 여부를 확인한다.

### 8.3 명세 인수인계 완료 기준

- 각 샘플의 사전 조건·정확한 입력·순서·판정·관찰값을 동료가 설명 없이 이해할 수 있다.
- 현재 코드 경로와 필요한 최소 시험 제어 지점이 연결되어 있다.
- 미구현/미정과 기존 구현의 회귀 검증이 분리되어 있다.
- DEC-01~DEC-10 중 샘플에 필요한 결정의 담당과 처리 상태가 기록된다.
- 샘플 4개가 정의되었다는 것과 전체 제품 QA가 끝났다는 것을 구분한다.

### 8.4 이후 변경 규칙

요구가 바뀌면 ID를 유지하고 변경 이유·날짜·기대값·영향 테스트를 남긴다. 테스트를 통과시키기 위해 설명 없이 기대값을 현재 버그에 맞추지 않는다. 기능 수정과 최적화는 동일 조건에서 기존 요구를 유지하는지 재검증한다.
