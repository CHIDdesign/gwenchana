# 시각 스타일 확정: 같은 바닥 (Same Floor) (2026-11-09)

에이전트 조사·채점으로 정한 구현 기준. 시안은 프로젝트 대표에게 요청. 앱 코드는 아직 안 바꿈. 실제 앱에서 렌더해 보지 않은 숫자이므로 첫 구현 때 왼쪽 패널 옆에서 먼저 확인할 것.

## 왜 이 스타일인가

결론: '같은 바닥'을 기본으로 하고, '계기와 기록지'의 기록 문법만 접붙입니다. '곁'은 버립니다.

채점(내 판단, 10점 만점. 순서는 취향 / 현대 패널 옆 어울림 / 놀란 운전자 가독성 / 11월 15일까지 구현 / 사람별 맞춤이 눈에 보임 / 슬롭 회피):
- 계기와 기록지: 8 / 8 / 7 / 8 / 9 / 9 = 49
- 같은 바닥: 9 / 10 / 9 / 8 / 8 / 9 = 53
- 곁: 6 / 5 / 8 / 6 / 7 / 5 = 37

같은 바닥이 이긴 이유: 구도의 근거가 취향이 아니라 측정값입니다. 왼쪽 패널의 미디어 줄 윗선을 앱까지 잇고, 패널 차와 같은 눈높이에 평면도를 놓으면 패널과 앱이 한 화면이 됩니다. 사용자가 말한 '규칙은 지키는데 구도가 없다'를 정확히 메웁니다. 첫 응답도 질문 하나와 증거 한 점뿐이라 놀란 사람이 가장 빨리 읽습니다.

계기와 기록지에서 가져오는 것 4가지: ① 실선 = 차 기록, 점선 = 추정, 빈 동그라미 = 운전자가 말함 (증인 원칙을 선으로 옮긴 것, 흑백 PDF에서도 삽니다) ② 오른쪽 창 끝까지 나가는 기록지 한 장 ③ 시각이 먼저 오는 장부 행 ④ 유리 위 충돌선 아래의 불투명 칩.
곁에서 가져오는 것 2가지: ① 사람이 직접 표시한 단계에 '내가 표시함'이라고 적는 정직함 ② 프로필이 바꾸는 변수를 제한한다는 원칙.

버린 것과 이유: 방위 링(차 그림이 화면에 둘이 됨), 꽃잎 도장(인증 마크처럼 보여 위조 신뢰 위험, M3 장식), 크림색 판(왼쪽 무채색 패널 옆에서 이물감, 베이지는 AI 디자인의 흔한 표식), 첫 응답 속도선(읽을 거리가 늘어남, 비교안 B로만), 꺾쇠가 화면 사이를 날아가는 안무(첫 응답과 기록 사이에 안내 10단계가 있어 눈에 안 보임).

이번에 직접 측정해 스펙을 바꾼 것(c2.jpg 표본, 저장소 글꼴 파일):
- 패널 바닥은 그라디언트가 아니라 위쪽만 흰색이고 그 뒤로 #F1F1F1이 평평하게 이어지다 #EEEEEE로 끝납니다.
- 패널 선 아래 미디어 줄은 #FFFFFF입니다. 그래서 레일도 흰색입니다. 파란 글자 버튼이 #F1F1F1 위에서 4.36:1로 실패하는데, 흰 레일에 두면 4.92:1로 해결됩니다.
- 에뮬레이터 앱 창 실측은 약 1682x1208로 공식 1700x1184와 다릅니다. 그래서 격자를 왼쪽 고정으로 정했습니다.
- Asta Sans에 tnum 기능이 있습니다(GSUB 확인). 앞선 세 시안의 '미확인'이 풀렸습니다. 굵기 축은 300~800입니다.
- 세 시안이 쓴 격자 합계는 다시 계산해 맞습니다(1700, 840, 412).


## 색과 기록 문법

- 원칙: 구조는 Pleos 무채색, 유채색은 '증언색' 하나, 파랑은 글자 버튼에만. 대비는 전부 sRGB 직접 계산. 출처 https://document.pleos.ai/docs/connect/guide/docs-design/foundations/colors
- 코드 주의: Theme.kt 83~84행 backgroundPrimary=흰색, Secondary=basic50 은 Pleos와 반대다. 아래 표대로 바꾼다. carStageTop/Bottom(86~87행)은 stage로 교체.
- stage(가로 창의 바닥, 라이트): 창 y 0~190 #FFFFFF → y 290 #F1F1F1 → y H-2 #EEEEEE. c2.jpg 패널 x=30 표본을 그대로 옮김(캡처 150→#FCFCFC, 190→#F1F1F1, 558→#EEEEEE). 벨트 경고가 뜬 상태 1장 기준이라 경고 없을 때 값은 미확인. 다크 #1D1E21→#131417 (패널 다크 값 미확인).
- rail(지평선 아래 줄): #FFFFFF / #131417. 패널 미디어 줄 표본과 같음. 파란 글자 버튼은 여기와 sheet·popup·휴대폰 window에만 둔다.
- horizon(지평선): #E0E0E0 2dp / #FFFFFF 12% 2dp. 패널 표본 값. 캡처가 절반 크기라 1dp인지 2dp인지 확정 못 함, 2로 시작.
- window(세로 창·휴대폰 바닥): #F7F8FA / #1D1E21. sheet(기록지): #FFFFFF / #131417. popup: #FFFFFF / #313236.

- ink2(보조 글자 기본): #44464E / #E0E1E6. #F1F1F1 위 8.33, 다크 #131417 위 14.11.
- ink3(가장 옅은 읽는 글자, Body M 이상만): #686A72 / #C7C9CE. #F1F1F1 4.78, #EEEEEE 약 4.65(계산), #FFFFFF 5.39, 다크 10.06.

- basic(보조 버튼): #131417 5% / #FFFFFF 5%, 눌림 10%. 비활성 흰색 20% + 2dp #131417 10% 테두리 + 글자 32%. 다크 수치는 Pleos 미확인, 대칭 추정.
- signal(증언색, 유일한 강조): #D32016 / #FF6A4D. 흰 글자 5.27, 흰 바탕 5.27, #F1F1F1 4.66, #F7F8FA 4.96. 다크 #1D1E21 5.89, #131417 6.51, 그 위 글자는 #131417 6.51. Pleos #FE3D16은 흰 글자 3.56이라 Pleos 자신의 4.5 규칙을 못 넘겨 같은 계열에서 어둡게 조정했다. 토큰에서 벗어나는 유일한 값. 눌림 #B81D13 / #FF8267.
- signal을 쓰는 곳은 넷뿐: ① 충격 꺾쇠 ② 시간 띠의 충돌선 ③ 다쳤어요·119·112 채움 버튼 ④ 비상등 도면(실제 빨간 물건).
- emergency: #AE251F(라이트·다크 공통, 공식 차량 알림 표본). 흰 글자 6.81. 부상 후 119 화면과 고속도로 2차 사고 경고에서만 창 전체를 칠한다. 패널과의 이음매를 일부러 깨는 유일한 화면이다. 그 위 버튼은 #FFFFFF 채움 + ink 글자.

- 안 쓰는 색: 초록(전화·연결됨 포함), 보라, 노랑·주황. 실제 텔테일을 그대로 재현할 때만 법규 색 허용. 전화 버튼은 filled 또는 signal.
- 도면 3색: 주인공 선 ink, 맥락 선(도로 끝·문서 윤곽) ink3, 충격 signal. 면 채움 없음.

- 그림자는 Pleos 3단계만: L1 y6 b24 8%, L2 y8 b32 16% + y2 b2 8%, L3 y20 b40 24% + y2 b4 20%. https://document.pleos.ai/docs/connect/guide/docs-design/foundations/shadow
- PDF: 종이 #FFFFFF, ink, ink2, hairline 0.5pt #C7C9CE, signal #D32016. 그림자·유리·둥근 판 없음.

## 글자

- 글꼴은 Asta Sans 하나(shared/res/font/asta_sans.ttf, 가변 300~800 직접 확인). Normal 400, Strong 700, Extrastrong 800. 이 대응은 내 판단이고 Pleos에 숫자 대응은 없다. https://document.pleos.ai/docs/connect/guide/docs-design/foundations/typography
- 숫자·시각은 전부 fontFeatureSettings = "tnum"(GSUB에 tnum 있음 확인). 값은 앞 글자보다 한 단계 굵게.
- Headline L 60/80 800: 첫 응답 질문, 고령자 모든 제목.
- Headline M 56/72 700: 초보 안내 단계 제목, 고령자 답 타일 글자.
- Headline S 48/64 700: 주행 중 한 줄, 차에게 묻기의 답.
- Title L 40/52 700: 화면 제목, 직장인 단계 제목.
- Title M 36/44 400: 직장인 체크 줄의 평소 상태. Title S 32/40 700: Large 버튼 글자, 장부 시각.
- Body L 30/38 400: 안내 본문 한 문장, Medium 버튼 글자. Body M 28/36 400: 장부 사실, 보조 글의 최소.
- Body S 26/34 700: Small 버튼만. Label M 24/28 400: 정차 화면의 범례·시간 눈금만. Label S 20/24: 차에서 사용 금지.
- Speed 112/134는 쓰지 않는다. 왼쪽 패널 속도계와 경쟁하고 큰 숫자가 판단처럼 보인다.
- Theme.kt 고칠 점: titleL·M·S가 Normal로 묶여 있다(128~130행). 위 표대로 쓴 곳에서 굵기를 준다.
- 한 화면에 글자 단계 3개까지, 이웃 단계 동시 사용 금지. 맛은 글꼴이 아니라 낙차에서 낸다(Headline L + Body L + Label M 가능, Title L + Title M 불가).
- 모든 제목·경고·본문은 왼쪽 정렬. 가운데 정렬은 버튼 글자뿐. https://developer.apple.com/videos/play/wwdc2025/356/ 어절 단위 줄바꿈 유지.
- 분량(내 기준, 한국어 공식 기준 미확인): 제목 14자, 본문 한 문장 40자, 한 화면 문장 3개.
- Pleos 5mm 기준이 글자 상자인지 실제 글자 키인지 미확인이므로 안전 문장은 48 이상.
- 휴대폰(가이드 범위 밖, 차 비율에서 정함): Display 34/44 800, Title 26/34 700, Subtitle 22/30 400, Body 17/26 400, Small 15/22 400, Label 13/18 400. 고령자 Display 40/52, Body 20/30, 15 미만 금지.
- PDF(pt): 제목 20/26 800, 절 12/16 700, 본문 10/15 400, 표 숫자 10/15 700 tnum, 주석 8/11 400.

## 모양

- 쓰는 반지름: 48(팝업), 40(기록지), 32(Large 버튼·유리 막대), 24(Medium·재생 버튼), 20(80 아이콘 버튼), 16(Small·64 아이콘 버튼·사진·토스트). 휴대폰 24(시트·도크), 16(버튼), 8(문서 썸네일). PDF 4pt. 이 외 금지. https://document.pleos.ai/docs/connect/guide/docs-design/components/actions/basic-button
- 동심 사슬: 기록지 40 - 여백 8 = 발밑 버튼 32. 유리 막대 32 - 여백 8 = 재생 버튼 24. 휴대폰 도크 24 - 8 = 버튼 16. Pleos 탭의 32-8=24를 앱 전체로 넓힌 것이고 Apple 최신 방향과 만나는 지점이다.
- 스쿼클은 기록지·팝업·유리 막대·선택된 토글에만(Pleos 토글의 60% 스무딩). 버튼은 Pleos 측정대로 일반 원호. 경로: 코너마다 p = r*1.6, 곡선 시작 (w-p, 0), 제어점 (w-0.155p, 0)과 (w, 0.155p), 끝 (w, p). 0.155는 45도 지점이 원과 같아지도록 내가 계산한 값이고 화면 확인은 못 함. Shape 하나로 만들어 네 코너 반지름을 따로 받는다.
- 버튼: Large 100/32, Medium 80/24, Small 64/16. 아이콘 버튼 80/20, 64/16. 눌림 95% 중심 축소 + 배경색, 영역 밖이면 취소, 뗄 때 실행, 0.25초 안 반응. 기존 Modifier.pressable을 쓴다.
- 헤더: 높이 144, 80/20 뒤로 + Title L, 아래 2dp 선. 단계 진행은 이 선이 왼쪽부터 ink로 채워지는 것 + 'Label M 3 / 10'. 10칸 막대 폐기. '‹ 이전' 글자 폐기.
- 표면은 3겹뿐: 0층 stage·rail(테두리·그림자 없음) / 1층 기록지(화면당 1장, L1) / 2층 유리·팝업(L2, 팝업은 L3). 판 안의 판 금지, sheet 안 구분은 여백과 hairline.
- 기록지는 카드가 아니다: 왼쪽 두 모서리만 40이고 오른쪽은 창 끝까지 나간다. 세로 창·휴대폰은 아래 끝까지, 위 두 모서리만 둥글다. 종이 질감·절취선 없음. 은유는 구도로만.
- 팝업: 큰 형 모서리 48, 좌우·아래 48, 버튼 100/32, 간격 24, 2dp #131417 5% 테두리. 글은 왼쪽 정렬. '사고가 아니에요' 확인과 기록 삭제 확인에만.
- 토스트: 모서리 16, #44464E, 좌우 40, 메시지 간 24.
- 3D: 패널과 같은 흰 차, 바닥색 = stage, 격자·안개 없음, 접지 그림자 하나, 카메라 약 70도로 높여 차를 작게. 궤적이 주인공. 3D 위 이름표·범례도 각지지 않게 r16 이상. three.js 유지(금지 문구 없음, 심사 영향 미확인).

## 유리가 허용되는 곳

- 허용 ①: 3D 재현 위 전송 막대(차·휴대폰). WebView HTML 안의 진짜 backdrop-filter. 뒤에 실제로 움직이는 장면이 있는 유일한 자리이고 시연의 유리 주인공이다. 재현이 재생을 시작한 뒤 투명도 250ms로 나타난다.
- 허용 ②: 사고 사진 전체 보기의 아래쪽 시각·위치 띠. 축소 사진을 늘린 흐림 + 78%.
- 허용 ③: 휴대폰 보험 접수·전화 원고·보내기 미리보기의 하단 도크. 흐림 없이 92% + 반짝임 테두리 + L2. 흐림이 없다는 점은 코드 주석과 보고에 그대로 적는다.
- 금지: 첫 응답, 119·112, 부상·대피, 차를 세우세요, 주행 중 전체, 안내 본문, 기록지, 진술, 숫자, 지문, 설정·동의, stage 위 고정 요소, PDF, 유리 위 유리, 색 입힌 유리, 고령자 프로필 전체.
- 근거: 조작 층만 유리, 내용 층은 평평하게, 지나가는 내용이 없으면 유리의 이득이 없다(https://developer.apple.com/videos/play/wwdc2026/8120/ , https://developer.apple.com/videos/play/wwdc2025/219/ ). 복잡한 배경 위 대비 저하 비판(https://www.nngroup.com/articles/liquid-glass/ )은 80% 고정과 최악 조건 계산으로 막았다. Pleos 가이드에 유리 허용·금지 문구는 없다.

## 사용자 유형별 차이

- 공통: 프로필이 바꾸는 것은 장면 종류, 밀도, 속도, 말의 양 넷뿐. 색·모서리·선·글꼴은 안 바뀐다. 사용자가 슬라이더를 만지지 않는다. 첫 설정에서 세 구도를 축소 그림으로 보여 주고 고르게 한다. 안전 명령(119·112·대피)은 세 사람 모두 같은 내용이다. 차와 휴대폰은 같은 프로필 값을 쓴다.
- 사회초년생(김하늘형, 같이 걷기): 시범 장면 중심, 한 화면 한 단계. 제목 Headline M y 176, 본문 Body L, 도면 480~800 전체 재생. 용어 풀이는 카드가 아니라 본문 아래 Body M 한 줄, 점선 밑줄 단어를 누르면 그 자리에서 펼침. 사진 안내는 한 장씩. 버튼 Large. 휴대폰은 한 장씩 넘김, 전화는 화면 4의 A.
- 바쁜 직장인(박준호형, 한 장 처리): 등뼈 장면이 주인공. 1~7칸(x 80~970)에 남은 일 전부를 Title M 행으로, 현재 행만 Title L 700에 버튼 Medium 하나, 끝난 행은 체크 + ink3로 한 줄 접힘. 9~12칸 기록지에 시각·장소·방향 세 줄. 도면 없음, 행 왼쪽 48 아이콘. 움직임은 끝 상태 변화만 250ms 안. 주 버튼 글자 '다 했어요'. 기록 화면은 재현 재생 없이 끝 프레임. 휴대폰은 한 스크롤 체크 목록, 전화는 화면 4의 B, 복사 한 번과 보내기 한 번.
- 고령자(이순자형, 한 문장·큰 답·가족): 지평선은 남기되 무대·기록지 나누기 없음. Headline L 한 문장 x 80 y 176 폭 1060. 답 타일 2개 x 80·860, y 760~1000, 폭 각 760 높이 240 r32, 글자 Headline M. 도면은 필요할 때만 240 하나. 글자 최소 Body L, ink3 쓰지 않음. 유리·탄성 전부 끔, 음성이 글자와 동시에. 시간 띠 대신 핵심 시각 세 줄. 끝은 항상 '이제 ○○님이 도와줘요'. 휴대폰 Display 40/52, 버튼 72/24, '○○님께 맡기기'. 가족 쪽은 같은 사건 화면을 그대로 연다. 가족 수신 신호는 코드에 없어 만들기 전에는 '통화가 끝났어요'까지만 표시한다. 타일은 버튼 규격 밖이라 가이드 허용은 미확인.

## 모션 원칙

- 원칙: 움직임 하나가 실제 상태 하나를 말한다. 신호로 시작, 1회 재생, 끝 프레임 정지. 끝 프레임만 봐도 뜻이 통해야 한다. https://document.pleos.ai/docs/connect/guide/docs-design/foundations/animation
- 주행 게이트: CarUxRestrictions의 NO_VIDEO 또는 주행 상태면 재생 없이 snapTo(끝 프레임). 재생 중 켜져도 즉시 끝 프레임. 재방문도 끝 프레임. https://developer.android.com/reference/android/car/drivingstate/CarUxRestrictions
- 화면 곡선: cubic-bezier(0.16, 1, 0.3, 1)(Pleos). 선 그리기 전용: cubic-bezier(0.4, 0, 0.2, 1). Pleos 곡선은 33% 시점에 90%라 선이 안 보인다. 다른 곡선 허용 여부 미확인.
- 시간은 Pleos 토큰만: 100, 150, 250, 300, 400, 450ms. 긴 이야기는 구간을 잇는다.
- 탄성은 2곳만: 충돌 표시 0.6/800(139ms에 9.5% 넘침), 저장 완료 체크 0.8/380(269ms에 1.5% 넘침). 나머지 넘침 없음, 색·투명도 1.0/1600. 고령자는 탄성 전부 없음. 사고 앱은 은행처럼 익숙함이 중요하다. https://design.google/library/expressive-material-design-google-research
- 사고 직후~정차 전: 색·투명도만, 그리기 없음.
- 단계 넘김: 제목 위치 고정, 글자 150ms 교차, 도면만 새로 그린다. 판이 미끄러져 들어오는 동작 없음. 버튼은 움직이지 않는다.
- 시그니처는 꺾쇠다. 앱 전체에서 빨간 꺾쇠는 같은 모양 하나(첫 응답, 궤적 끝, 휴대폰 도면, PDF). 이동시키지 않고 같은 자리에서 같은 물건으로 반복해 알아보게 한다.
- 기록 화면 첫 진입이 이 앱의 쇼 순간: 속도선이 그려지고 펜 끝이 지나는 시각의 장부 행이 150ms로 찍힌다(조각 5). 유리 전송 막대는 그 뒤 250ms로 나타난다.
- 로딩은 Pleos 고리 2종만(파일 미수령). % 숫자 금지.
- 구현: 새 라이브러리 없이 Compose Canvas + PathParser + PathMeasure + Animatable. 시계 값 하나로 모든 순간을 그려 단위 테스트한다. Art.kt의 rememberInfiniteTransition 4곳 제거. 윤곽마다 경로 분리, 남은 길이 6% 미만이면 그리지 않음. 무한 반복 금지, 3D 재현은 3회 뒤 정지(이미 구현). Compose 1.6.6에서 PathParser·PathMeasure 클래스 존재만 확인, 실제 Android 렌더는 미확인.
- 프로필별: 초보 전체 재생, 직장인 끝 상태 변화만 250ms 안, 고령자 탄성 없이 획마다 450ms 순차 + 음성 동시.

## 위험과 미확인

- 이 스펙은 숫자와 캡처 표본으로만 만들었다. 시안도 앱도 렌더하지 않아 왼쪽 패널 옆 실제 어울림은 미확인. 첫 구현 때 c2 화면과 나란히 놓고 먼저 본다.
- 패널 색과 지평선은 벨트 경고가 뜬 캡처 1장의 표본이다. 경고 없는 상태, 다크 모드, 실차는 미확인.
- 앱 창 크기가 공식(1700x1184)과 에뮬레이터 실측(약 1682x1208)이 다르다. 실차 모양도 미확인. 왼쪽 고정 격자로 막았지만 840 세로 창과 소형 화면은 미시험.
- Pleos Figma 아이콘은 일부만 봤다. 삼각대·시설물·가족이 없으면 직접 그린다.
- WebView의 backdrop-filter와 WebGL 위 비용, 실차 GPU 미확인. 휴대폰 도크는 진짜 흐림이 아니다.
- 새로 만들어야 하는 기능: 차에게 묻기(코드 검색 0건), 가족 수신 신호, 메모리 카드 안내.

## 유리 Compose

전제: Compose UI 1.6.6, Material3 1.2.1. 새 라이브러리 금지(Haze 최신판은 Compose 대폭 상향 필요, https://chrisbanes.github.io/haze/latest/changelog/ ). 아래 코드는 컴파일 안 함(미확인). Pleos.basic00, Pleos.shapeL, pleosShadow는 Theme.kt에 있음 확인.

// shortcut: blurred 없으면 진짜 흐림이 아니다. 휴대폰 도크가 이 경우. 실시간 유리가 필요하면 Compose 올린 뒤 Haze로 교체.
@Composable
fun GlassBar(
    blurred: ImageBitmap?,       // 사진 위 띠에서만 전달
    photoOrigin: Offset, photoSize: IntSize,
    solid: Boolean,              // 고령자·주행 중이면 true
    modifier: Modifier = Modifier,
    shape: Shape = Pleos.shapeL,
    content: @Composable BoxScope.() -> Unit,
) {
    var origin by remember { mutableStateOf(Offset.Zero) }
    Box(
        modifier
            .onGloballyPositioned { origin = it.positionInRoot() }
            .pleosShadow(2, shape)
            .clip(shape)
            .drawWithCache {
                val outline = shape.createOutline(size, layoutDirection, this)
                val rim = Brush.verticalGradient(0f to Color.White.copy(.85f), .5f to Color.White.copy(.15f), 1f to Color.Black.copy(.10f))
                val stroke = Stroke(2.dp.toPx()) // clip 때문에 안쪽 1dp만 보임
                onDrawWithContent {
                    when {
                        solid -> drawRect(Pleos.basic00)
                        blurred == null -> drawRect(Pleos.basic00.copy(alpha = .92f))
                        else -> {
                            val o = origin - photoOrigin
                            drawImage(blurred, dstOffset = IntOffset(-o.x.roundToInt(), -o.y.roundToInt()), dstSize = photoSize, filterQuality = FilterQuality.Low)
                            drawRect(Pleos.basic00.copy(alpha = .78f))
                        }
                    }
                    drawOutline(outline, rim, style = stroke)
                    drawContent()
                }
            },
        content = content,
    )
}

## 모션 구현 방법

결론: 새 라이브러리 없이 지금 코드의 방식(Compose Canvas, 그리기 단계에서만 값 읽기)으로 만듭니다. Art.kt에 작은 그리기 함수를 하나 더하는 정도입니다.

비교
1) Compose Canvas + PathParser + PathMeasure + Animatable(추천). 추가 라이브러리 0개. 경로 글자 수를 직접 잰 값은 차 조각 532바이트, 비상등 217바이트이며 8개 합계는 4~8KB로 추정합니다. 프로젝트가 쓰는 Compose 1.6.6(BOM 2024.04.01)의 실제 클래스에서 PathParser.parsePathString/toPath, PathMeasure.getSegment/getPosition/getTangent가 있음을 javap로 확인했습니다. 충격 각도, 전송 응답, 현재 읽는 문장 같은 실제 값을 넣을 수 있고, 시계 값 하나로 어느 순간이든 그릴 수 있어 단위 테스트도 됩니다.
2) AnimatedVectorDrawable(pathData 변형 가능). 경로 크기는 1번과 비슷합니다. 플랫폼 버전은 API 25부터 RenderThread에서 돌아 가장 부드러울 수 있지만, 공개 메서드는 start/stop/reset 위주라 특정 시점으로 이동하거나 실제 데이터로 몰기 어렵습니다. Compose의 rememberAnimatedVectorPainter는 updateTransition으로 돌아 RenderThread 이점이 설명돼 있지 않고, animation-graphics 의존성이 필요한데 이 프로젝트의 Gradle 캐시에는 없습니다. 입력값이 없는 조각 7에는 쓸 수 있지만, 도구를 둘로 나눌 이유가 없습니다.
3) Lottie. Apache-2.0. AAR 압축 크기 lottie 6.6.4 426,899B + lottie-compose 133,544B = 약 560KB에 조각별 JSON이 더해집니다. app/build.gradle.kts에 isMinifyEnabled가 없어 R8로 줄지도 않습니다. After Effects 제작 과정도 필요합니다. APK 증가량 실측은 미확인입니다.
4) Rive. MIT. 공식 표 기준 ARM-v8a 다운로드 2.40MB, 설치 7.03MB이고 x86_64는 표에 없습니다. 2차 시연은 x86_64 에뮬레이터라 그 ABI도 필요합니다. Wikimedia 시제품은 AAB가 약 14.8MB 늘었습니다(한 사례). 8개 조각에는 과합니다.
크기 순서: 1번과 2번이 비슷하게 가장 작고, 그다음 Lottie, Rive입니다. 1번을 고른 이유는 크기보다 실제 값을 넣을 수 있기 때문입니다.

구현 뼈대(컴파일 안 함, 미확인)
val clock = remember { Animatable(0f) }
LaunchedEffect(signal, calm) { if (!signal) return@LaunchedEffect; if (calm) clock.animateTo(END, tween(END.toInt(), easing = LinearEasing)) else clock.snapTo(END) }
Canvas(modifier) { scale(size.minDimension / 48f, Offset.Zero) { val t = clock.value; /* 단계별 그리기 */ } }
private val pm = PathMeasure()
fun DrawScope.ink(p: Path, c: Color, s: Float = 0f, e: Float = 1f, w: Float = 3.6f) { if (e - s < 0.0001f) return; if (s == 0f && e == 1f) { drawPath(p, c, style = Stroke(w, cap = StrokeCap.Round, join = StrokeJoin.Round)); return }; pm.setPath(p, false); val L = pm.length; val d = Path(); pm.getSegment(s * L, e * L, d, true); drawPath(d, c, style = Stroke(w, cap = StrokeCap.Round, join = StrokeJoin.Round)) }
경로 준비: remember { PathParser().parsePathString(d).toPath() }
변형: 숫자만 정규식으로 찾아 두 문자열 사이를 lerp한 뒤 parsePathString으로 다시 읽습니다(변형이 100~325ms뿐이라 매 프레임 파싱을 허용, shortcut: 끊김이 보이면 FloatArray로 교체).
곡선과 탄성: 시계 값 t를 받는 순수 함수로 계산합니다. 시험 페이지의 seg/spring 함수를 그대로 옮기면 됩니다. 탄성 공식: 1-exp(-z*w*t)*(cos(wd*t)+z*w/wd*sin(wd*t)), w=sqrt(강성), wd=w*sqrt(1-z*z).

지켜야 할 점
- 주행 중 재생 금지: animate 대신 calm을 쓰고, calm이 도중에 false가 되면 snapTo(END)로 바로 마지막 프레임을 보여 줍니다.
- rememberInfiniteTransition을 쓰는 이 조각들에서는 전부 제거합니다.
- 차에서는 80의 배수 dp(80·160·240)로 그립니다. 휴대폰은 밀도 420이라 맞출 필요가 없습니다.
- 색은 Pleos 토큰(textPrimary, negative 등)을 씁니다. 시험에 쓴 #FF4316은 화면을 보고 잡은 임시 값입니다.
