# 정확도·최적화에 쓸 수 있는 오픈소스·공개 자료 (2026-11-02)

코드는 바꾸지 않은 조사 결과다. 표시 뜻은 다음과 같다.
- **확인**: 이번에 공식 문서나 원문을 열어 봄
- **조사만**: 조사 에이전트가 페이지에서 봤고 메인이 다시 열어 보지는 않음
- **계산**: 물리 계산일 뿐 실험하지 않음
- **미확인**: 근거를 못 봄

라이선스 내용은 법률 자문이 아니다. 모든 정확도 이득은 **아직 우리 앱에서 재지 않은 값**이다.

## 실차 원칙으로 다시 본 추천 (사용자 지시, 2026-11-02)

앱은 실차 Pleos SDK로 얻는 정보만 써야 한다. 게임은 그 값을 대신 만드는 시험장이다.
- **1·3번 (감지·충격 방향):** 가속도 센서는 Pleos SDK가 아니라 안드로이드 표준 센서이고, 실차 개방 여부가 미확인이다. 센서 없이 SDK 속도·에어백만으로도 동작해야 하며, 센서는 있을 때만 쓰는 보강으로 둔다.
- **2번 (평가):** 게임 정답은 PC 쪽 채점에만 쓴다. 앱 판단과 화면에는 넣지 않는다.
- **5·6번 (차 인식·추적):** 실차엔 영상 API가 없다(Camera2 사진 1장, 개방 미확인). 게임 영상으로만 좋아지면 실차 성능이 아니므로 시연에서 그렇게 말하지 않는다.

## 지금 코드의 약점

| 위치 | 현재 | 약점 |
|---|---|---|
| `Crash.kt` `ImpactSensor` | 수평 가속도 최대값 ≥ 2.5g | 아주 짧은 순간의 큰 값도 사고로 봄. 2.5g가 20ms면 속도 변화는 약 1.8km/h(계산) |
| `Crash.kt` 충격 방향 | 최대값이 나온 샘플 하나의 방향 | 잡음과 센서 잘림에 약함 |
| `Crash.kt` 시각·센서 속도 | `currentTimeMillis`, `SENSOR_DELAY_GAME` | 적분에는 센서의 `event.timestamp`가 더 맞고, 충돌은 짧아 샘플이 적음 |
| `Recorder.kt` `trackPoses` | 속도·회전 추측항법, GPS 보정 없음 | 시간이 길수록 오차가 쌓임 |
| `Vision.kt` | 프레임별 단독 판단, Lite0, 가장 넓은 상자 | 거리가 튀어도 걸러지지 않음 |
| `Report.kt` Validator | 정규식 대조 | 표현을 바꾸면 놓치거나, 맞는 문장을 버림 |
| `app/build.gradle` | `buildTypes`·R8 없음 | release 크기를 잰 적 없음 |

## 13일 안에 할 만한 것 (추천 순서)

### 1. 사고 감지를 "속도 변화량"으로 판단 (난이도 하, 실차 유효)
- **근거(확인):** 미국 EDR 규정 [49 CFR 563.5](https://www.law.cornell.edu/cfr/text/49/563.5)는 150ms 안에 **앞뒤 방향** 속도 변화 8km/h 이상을 기록 기준으로 둔다.
- **계산:** 평균 약 1.5g다. 건조한 노면의 급제동을 약 1g로 보면 150ms에 약 5.3km/h라서 이 기준에 못 미친다. 4g에서 잘려도 150ms면 21km/h까지 쌓여 기준을 넘는다.
- **방법:** 가속도를 `event.timestamp`로 150ms 동안 적분해 판단하고, 센서는 `SENSOR_DELAY_FASTEST`로 받는다.
- **주의 1:** 이 규정은 EDR 기록 기준이지 "사고 판정" 기준이 아니고, 측면은 다루지 않는다. 수평 벡터로 넓히는 건 우리 변형이다. 그대로 믿지 말고 2번으로 조정한다.
- **주의 2:** 조사에 나온 Google 등의 감지 특허 방식은 베끼지 말고, 공개 규정과 물리 계산으로 만든다.

### 2. BeamNG 사고 기록으로 기준값 평가 (난이도 하~중, 게임 전용 도구)
- 우리에겐 정답이 있는 시험장(`crash_test.py`, `game/bridge/runs/*.jsonl`의 손상도·상대 위치)이 있다. 공개 충돌 데이터보다 이게 빠르다.
- 정면·측면·후방·약한 접촉, 그리고 사고가 아닌 급제동·연석·과속방지턱을 돌려 **감지율·오탐·충격 방향 오차**를 표로 만든다.
- 심사 때 쓸 수 있는 실측 숫자도 함께 생긴다.
- 한계: 게임 값은 실차 값과 다르다. 실제 충돌 파형과의 대조는 NHTSA 자료(아래 보류)가 필요하다.

### 3. 충격 방향을 "적분한 방향"으로 (난이도 하, 실차 유효)
- 최대값 샘플 대신 충돌 구간의 가속도 벡터를 적분해 방향을 낸다. 충격량의 방향이므로 물리적으로 맞고, 1번과 코드를 공유한다.
- 조사에서 나온 SAE 2015-01-1448(오차 2도 이내)과 AAFS 2008 C40은 메인이 원문을 못 읽었다(**조사만**). 인용하지 말고 2번에서 직접 잰다.

### 4. 경위서 숫자를 구조로 막기 (난이도 중, 실차 유효)
- **근거(확인):** [Claude structured outputs](https://platform.claude.com/docs/en/docs/build-with-claude/structured-outputs)는 `output_config.format`으로 JSON schema를 강제하고, 쓰고 있는 `claude-opus-5-5`를 지원한다. `enum`은 되고 `minimum`·`maximum`은 안 된다. `enum` 값의 대소문자는 달라질 수 있다.
- **방법(우리 설계, 문서에 있는 방식 아님):** 문장에 숫자 대신 `{{fact:12}}`를 쓰게 하고, 앱이 로그 값으로 채운다. Validator는 보조로 남긴다.
- 이득: "LLM 숫자는 로그와 대조" 규칙이 "LLM은 숫자를 쓰지 못함"으로 강해진다.

### 5. 차 인식 모델을 EfficientDet-Lite2로 (난이도 하, 실차 유효)
- **근거(확인):** [Google 표](https://developers.google.com/edge/litert/libraries/modify/object_detection) 기준 COCO mAP가 25.69%에서 33.97%로, 크기가 4.4MB에서 7.2MB로 는다(Pixel 4 CPU 37ms → 69ms). [MediaPipe 문서](https://developers.google.com/edge/mediapipe/solutions/vision/object_detector)도 Lite2를 더 정확하지만 느린 쪽으로 설명한다. 사고 뒤 프레임 몇 장만 처리하므로 지연은 문제가 안 된다.
- MediaPipe는 그대로 두고 모델 파일과 이름만 바꾸면 된다.
- **주의:** MediaPipe 문서에 모델 자체의 라이선스가 없다. 지금 Lite0처럼 메타데이터에 Apache-2.0이 적힌 공식본을 찾아야 한다.

### 6. 프레임 간 추적으로 거리 안정화 (난이도 하~중, 실차는 카메라가 있어야 함)
- 충돌 전 3~5프레임을 상자 겹침(IoU)으로 이어서 폭을 평균 낸다. 라이브러리 없이 수십 줄이다.
- 개념 참고용(**조사만**): ByteTrack, OC-SORT(둘 다 MIT). SORT는 GPL-3.0이라 쓰지 않는다.
- 실차에서는 지금 사진 1장뿐이라, 게임 시연에만 효과가 있다.

### 7. 기록 위변조 표시 강화 (난이도 하, 실차 유효)
- 해시 체인 자체는 전체를 다시 계산하면 위조할 수 있다. 조사 보고의 "중간 삭제가 드러남"은 **마지막 해시가 다른 곳에 있을 때만** 맞다.
- 이미 있는 폰 동기화의 "기록 지문"을 사고 직후 폰에 보내면 외부 보관이 된다. 여기에 Android Keystore 서명을 더한다.
- C2PA(`c2pa-android`, Apache/MIT, **조사만**)는 표준이지만 용량과 차 단말 지원이 미확인이라 그다음이다. RFC 3161은 인터넷이 필요하고 법적 효력이 미확인이다. "법적 증거 효력"이라고 말하지 않는다.

### 8. release 빌드와 크기 측정 (난이도 하)
- R8·리소스 축소를 켜고 release APK를 재는 것부터 한다. 제출에 어차피 필요하다.
- [Baseline Profiles 문서](https://developer.android.com/topic/performance/baselineprofiles/overview)는 첫 실행 코드가 약 30% 빠르다고 적는다(**조사만**).
- **x86_64를 빼면 안 된다.** 조사 추천엔 "arm64만"이 있었지만 2차 시연이 x86_64 에뮬레이터다. 뺄 경우 시연용과 실차용 APK를 따로 만들어야 한다.

### 9. 폰 앱 서버는 실서비스 준비 때 (공개 전 필수)
- **확인:** [`dataSync`는 24시간 중 6시간 제한](https://developer.android.com/develop/background-work/services/fgs/timeout)이고, `onTimeout()` 뒤 몇 초 안에 멈추지 않으면 앱이 죽는다. 폰 앱은 이미 멈추도록 처리했다(`Sync.kt:168`). 다만 멈춘 뒤엔 알림이 안 오므로 실서비스엔 푸시가 필요하다.
- 후보(**조사만**): [Durable Objects WebSocket Hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/). 이미 있는 relay를 확장하는 길이다. FCM 문서와 무료 요금제 가능 여부는 미확인이다.
